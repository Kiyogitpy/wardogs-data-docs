# Wardogs — Item and Player Actions
*Extracted from every `BHActionDefinition` and `WDActionDefinition` asset in the exports (155 assets: 134 `BHActionDefinition` and 21 `WDActionDefinition`), plus the item-side bindings in `ID_*` item assets. Cooked data only (UE 5.7, `++Wardogs+Live-CL-516586`). The tables are generated by [`_tools/action_tables.py`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/_tools/action_tables.py); do not edit them by hand.*

> **Labels.** **Data** = read from an exported asset. **Derived** = a reading of the names and the data together, not confirmed in native code. **Native** = traced in the game binary. **Not traced** = neither the data nor the code read says. This page has no **Native** claims; every behavior note is **Data** or **Derived** unless it says otherwise.

An *action* is something the character does: fire, reload, sprint, heal, throw, emote. An action definition asset describes one action: its tag, which blueprint runs it, and which other actions it blocks, interrupts or buffers. Items choose which action tag each input starts. How the pieces connect:

1. An item ([`ID_Bandage`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Items/Consumables/Bandage/ID_Bandage.json)) lists *input behaviors*: input tag `Input.NamedActions.Appliable.PrimaryUse` starts action tag `Action.Appliable.Bandage.PrimaryUse` (**Data**, section 7).
2. The action tag finds its `DA_Action_*` definition (sections 4 and 5). The definition names the class that runs the action and the rule list for conflicts with other actions.
3. Item-specific numbers (heal amount, how the use time is decided, units consumed) are on the item, not on the action (section 6).
4. Some actions also apply GameplayEffects while they run (section 8).

The earlier overview is [GameMechanics §4](Wardogs_GameMechanics_v2.md#4-action-definitions-actions-116-bhwd-action-definitions). This page is a separate page, not a section of GameMechanics, because the tables are generated, are about 150 rows, and join three asset families (actions, items, effects) that GameMechanics §4 only lists by folder.

## 3. Response rules (`ActionResponseData`)

Each entry has a response type and up to six lists. The type decides how the lists are read. The plain meanings below are **Derived** from the names and the entries; how the action system evaluates them is **not traced**.

| Response type | Plain meaning |
|---|---|
| `Interrupt` | Starting this action cancels the listed actions if they are running (bandage use cancels sprint). |
| `Block` | While this action runs, the listed actions cannot start (reload blocks inspect and a second reload). |
| `BlockingStates` | This action cannot start while the character has one of the listed states (reload is refused when `Vitality.Critical` or `Vitality.Dead`). |
| `InterruptCategories` | Like `Interrupt`, but by context flag (an emote cancels other emotes). |
| `BlockCategories` | Like `Block`, but by context flag. |
| `Buffer` | If the listed action is requested while this one runs, the request is queued. A `FullBuffer` entry keeps it queued until the running action ends (its time is not read). A `PartialBuffer` entry keeps it for `BufferTime` seconds counted from the request. If the running action ends first, the queued action starts at once; if the time runs out first, the request is dropped. Static reading of `0x524E600`, `0x5265BC0` and `0x524ECB0` (section 10.3). |
| `InterruptBuffered`, `InterruptAndBuffer`, `InterruptOnComplete` | Combinations of interrupt and buffer, or an interrupt tied to completion. |
| `RequiredStates` | The character must have the listed state to start the action. |
| `None` | Present but empty. |

Tags in the tables drop the `Action.` prefix (`Player.Sprint` is `Action.Player.Sprint`). Tags under `BlockingStates` and `RequiredStates` drop `State.Player.`; category tags drop `Action.Context.`. `Block` and `Interrupt` lists can also name states such as `State.Player.Movement.Custom.Ladder`; those appear in full.

## 4. Definitions and rules by item family

Each family has two tables. The first gives the definition (what the asset is and which items bind it). The second gives the conflict rules. Rows with identical contents are merged and list their assets together. "Bound by items" lists the `ID_*` item assets whose input behaviors start the action (first five); `—` means no item binds it (movement, UI and generic weapon actions are started by the character, not by an item) and `release only` means an item only completes it.

How to read it:

- **Heal / attribute.** The attribute the item changes and the amount. `(delta)` means `bApplyAsDelta` is true (added to the current value). For the defibrillator the flag is not stored, so the mode is not confirmed. Heal amounts are also on [Items §5](Wardogs_Items_v2.md). Heal rates, applied effects, use costs and the medic skills that change them are on [Medical and Healing](../game-features/Wardogs_Medical_v1.md). **Data**.
- **Time method.** `AnimationLength`: the use lasts as long as the animation. `AnimationNotifier`: it completes at an animation notify (`Heal`). `UntilItemEmptyOrTargetFull`: the use continues until the item runs out or the target is full (fuel can, repair tool, resuscitator). The method name is **Data**; the seconds are the montage lengths in section 6.1 (**Data (Blueprint CDO)**, [round 17 evidence](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/docs/evidence/round17-blueprint-defaults.md)).
- **Consumed per use.** `AmountConsumedOnUse` (1 for almost all). **Data**.
- **World interaction.** A context class names the interaction that targets another player or a vehicle (`WDHealPlayerInteractionContext`, `WDVehicleRepairInteractionContext`). **Data**.
- **Container.** `bContainerAppliable` marks items that hold a quantity (fuel, repair charge). **Data**.

### 9.1 Input to action: the native part (round 91, static reading)

Chain as far as the exports and the executable show it. Key to input action: the input mapping contexts ([`IMC_Player`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/GameMechanics/Player/PlayerCharacter/Inputs/IMC_Player.json) and others, [GameMechanics section 5](Wardogs_GameMechanics_v2.md#5-input-playerplayercharacterinputs)) map each key to a `BHInputAction`, which carries an `InputTag` (`Input.NamedActions.*`). The action base class `UBHGameplayAction` holds a multicast delegate `OnInputTriggered(tag)` (offset `+0x28`) and its own `InputMappingContext` (`+0x50`). An action Blueprint waits for a tag with the `WaitForInput(action, tag)` async node (class `UBHGameplayAsyncAction_WaitForInput`, tag stored at `+120`, flag byte at `+128`): its activation (`0x5250200`) adds a delegate bound to the node's `OnInputTriggered` function to the action's list, and the function (`0x52694E0`) fires the node's `Triggered` output only when the tag it receives equals the stored tag. So a running action can react to a key while it runs (release, repeat); the public call that starts an action is `TryActivateAction(tag, context)` on the action system component, whose callers were not traced.

Where the starting call is made is Blueprint logic (the character and the action classes) that the exports do not contain, so which tag starts which action is **NOT LOCATED** as a table. ## 10. Action Blueprints (round 86)

### 10.2 Chamber and reload buffering

**`B_Action_ChamberWeapon`** (bytecode, functions `BP_CanActivate`, `BP_OnCancel`, `CheckInterrupt`, the ubergraph):

1. It can start only when the magazine slot (`Item.Attachment.Magazine`) holds at least one `Item.Ammo` and the chamber slot (`Item.Attachment.Chamber`) is empty (`BP_CanActivate`, offsets 438 to 647).
2. `bCanActivateDuringItemEquippingOnServer` is true: on the server it may start while the weapon is still being equipped.
3. It plays the animation tag `Animation.Asset.Weapon.Chamber`. The animation notify named `Chamber` moves one round from the magazine's ammo slot to the chamber slot (a move operation of amount 1, ubergraph offsets 1124 to 1772). **SERVER**: that move is registered only when the code runs on a dedicated server and the pawn is not bot controlled (`IsDedicatedServer` and `IsBotControlled` tests at offsets 956 to 1110). Clients only set `bChamberComplete` and reset the reload state.
4. The notify `RechamberComplete` sets `bRechamberComplete`. The action listens for the action events of `Action.Weapon.Fire` and `Action.Weapon.Reload`: a queued buffer (event type `BufferQueued`, and for reload also `BufferedActivation`) sets `bFireBufferQueued` or `bReloadQueued`, a cancellation or completion clears it. `CheckInterrupt` ends the action early (`Complete`, after `ResetReloadState`) as soon as `bRechamberComplete` is true and a fire or reload is queued, so the buffered shot or reload does not wait for the end of the animation.
5. `BP_OnCancel` plays the audio event `Audio.Event.Weapon.Reload.Cancelled` for an external or interrupting cancel, and returns the response `Buffer` when the chamber was not yet complete (`None` otherwise, and on a rollback). That return value (`EBHGameplayActionCancellationResponse`: `None` or `Buffer`) is the Blueprint side of re-buffering: it asks the action system to queue the chamber action again. [`DA_Action_Chamber`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/GameMechanics/Actions/Weapons/DA_Action_Chamber.json) is the only definition with `bRebufferAction` set (section 2). The flag is read in the native routine at `0x524ECB0` (**Native**, static reading): after an action ends, each queued request that waited on it is checked again, and when the check says it is still held back by a buffer response, the request is re-queued only if the requested action's definition has `bRebufferAction`. Everything else (started, blocked, interrupted) is decided by that check; a request that is no longer allowed is simply dropped. The path that handles the `BP_OnCancel` return value itself was not traced.

The same pattern appears elsewhere. `B_Action_Reload` keeps `bFireBufferQueued` and `bAdsBufferQueued`, so a shot or ADS request made during a reload is remembered and replayed. `B_Action_Sprint` and `B_Action_TacSprint` return `Buffer` from `BP_OnCancel` when the cancelling action is `Player.Traversing.Vaulting` and the cancellation is an interruption, so a sprint cut off by a vault is queued again. The bow pair checks the other action's buffer with `IsActionBufferedByTag`: `B_Action_BowDraw` refuses while `Action.Weapon.Bow.Reload` is buffered, and `B_Action_BowReload` acts on a buffered `Action.Weapon.Bow.Draw`.

`B_Action_Reload.BP_CanActivate` is two checks: the reload is not blocked by a gamepad interaction (`WDInteractionStatics::IsGamepadInteractionBlockingReload`) and `WDInventoryStatics::CanPerformReloadWithContext` is true.

### 10.3 `FullBuffer` and `PartialBuffer` in the data

Every buffered-response entry in the 155 action definitions, grouped by type and time (**Data**, generated). The engine type is `EBHActionBufferType` (`FullBuffer` = 0, `PartialBuffer` = 1); each entry is a tag, a type and a time.

What the table shows (**Derived**, no native proof): 20 of the 22 `FullBuffer` entries have a time of -10, a value that cannot be a duration, so the type seems to hold the request until the blocker ends instead of for a time. The other two `FullBuffer` entries (bow reload to bow draw, defibrillator reload to defibrillator use) are the paired actions that read each other's buffer. Every `PartialBuffer` entry has a positive time between 0.5 and 5 s. **Native handling** (static reading of the restored executable, not confirmed at runtime). When a request is held back by a running action's `Buffer` entry, the queue routine at `0x524E600` writes one record per blocking action, each with an expiry time. For `PartialBuffer` the expiry is the current simulation time plus `BufferTime` x 1000 ms (a negative time counts as 0). For `FullBuffer` the expiry stays at -1 and `BufferTime` is never read, which is why 20 of the 22 `FullBuffer` entries can carry -10 without effect. Each simulation step the routine at `0x5265BC0` removes every record whose expiry is above 0 and has passed; a request with no records left is dropped and a "buffer expired" event is sent (event type 6). When a blocking action ends (complete or cancel), `0x524ECB0` removes its record, and once a request has no records left it is tested again: allowed means it starts, still held back means it is re-queued if `bRebufferAction` is set (section 2), anything else drops it.

What a player experiences, as a reading of that logic: a `PartialBuffer` input is remembered for the listed time (half a second for a lean pressed during a sprint, 2 s for a crouch or prone pressed while falling or jumping, 3 s for a sprint pressed in a fall or jump, up to 5 s for a reload pressed on a ladder or in water) and fires the moment the blocking action ends; if the block lasts longer, the input is lost. A `FullBuffer` input (reload during equip, aim during a mantle or climb cancel, chamber during a sprint) waits as long as the blocker runs, with no time limit, and fires when it ends. A queued request is also removed when the buffered action is cancelled by handle (`0x524EC20`).
