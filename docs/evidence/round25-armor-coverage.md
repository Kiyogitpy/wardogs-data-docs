# Round 25: which armor covers which hit location

Generated by `python _tools/weapon_damage_locations.py --json`; verified by `--check`. Output:
[`assets/data/weapon-damage-locations.json`](../../assets/data/weapon-damage-locations.json).

## Why

Round 24 evaluated armor only at Torso.Upper (vests) and Head (helmets). The rule in
[DamagePipeline v2 section 7.6](../../pipelines/Wardogs_DamagePipeline_v2.md) is not tied to those two
locations. The target's hook keeps the first armor tag in context order whose item lists the hit
location in `CoveredHitLocations`, and removes the others (round 8, `docs/evidence/round8-armor.md`).
So every item must be evaluated at every location it lists, and an item has no effect elsewhere.

SuperHeavy ("Torso, pelvis, upper arm") matches the data.

## Stated in the data versus inferred

Stated in data: the covered locations per item, the context tag, R, and that Ghillie items have no
stages and no coverage list. Stated in documented findings: the covering rule (section 7.6) and that
`B_AmmoTypeEffectiveness` turns R into the factor `1 - R x ammo scalar / 100` (section 7.3).

Inferred, not read from a single data field:

1. A vest and a helmet never cover the same location, so only one covering piece is ever in the
   target context. The check confirms this from the data (no location is covered by both kinds).
   Equipping both therefore never needs the "first in context order" tie-break.
2. Two vests or two helmets are not equipped at once. The game has one slot of each kind; I assumed
   this and did not read the slot definition in this round.
3. Ghillie items are treated as no effect. Their fragment has no stages and no coverage list, so the
   rule cannot select them at any location. Whether a Ghillie context tag has rows in other tables is
   not covered by this round.

## Effect per location

Multiplier on M4 FMJ at point blank, armored over unarmored (from `meta.armor_effect` in the JSON). For
FMJ the factor is `1 - R/100`. Other ammo types use their own scalar, so read each row of the JSON as
`damage[location][class] / damage[location]["None"]`.

| Location | Kind | Classes that change the result (FMJ multiplier) | Classes with no effect |
|---|---|---|---|
| Head | helmet | Light 0.70, Pilot 0.70, Medium 0.60, Heavy 0.50, Tank 0.45, SuperHeavy 0.40 | none |
| Neck | helmet | Heavy 0.50, Tank 0.45, SuperHeavy 0.40 | Light, Medium, Pilot |
| Torso.Upper | vest | Light 0.70, Medium 0.60, Heavy 0.50, SuperHeavy 0.40 | none |
| Torso.Middle | vest | same as Torso.Upper | none |
| Torso.Lower | vest | same as Torso.Upper | none |
| Pelvis | vest | SuperHeavy 0.40 | Light, Medium, Heavy |
| Arm.Upper | vest | SuperHeavy 0.40 | Light, Medium, Heavy |
| Arm.Lower, Arm.Hand, Leg.Thigh, Leg.Calf, Leg.Foot | vest | none | all |

Nothing in the generated table has armored damage above unarmored damage.

## Evidence for each class

Each class is evaluated by the same `damage_tables.evaluate` call as in round 24, passing the item's
context tag as the covering target tag; only the set of locations at which it is passed changed.
Round 24 cells at Torso.Upper (None to SuperHeavy vest) and Head (None to SuperHeavy helmet) are
reproduced exactly for all 190 weapon x ammo rows, and so are the six round 24 unarmored location
columns. The three independent verifier values are re-derived for M4 FMJ:

| Case | Unarmored | Armored (this tool) | Verifier |
|---|---:|---:|---:|
| Torso.Middle into Heavy vest | 27.16 | 13.58 | 13.6 |
| Neck into Heavy helmet | 49.35 | 24.68 | 24.7 |
| Arm.Upper into SuperHeavy vest | 15.12 | 6.05 | 6.05 |

Pilot and Tank helmets are new relative to round 24, which listed only None to SuperHeavy.
Their R values (30 and 55) are in the item data; the armor rule table
`DT_GlobalDamage_ArmorData` and the ammo-effectiveness rows key on the `Meta.Damage.Helmet`
parent, so they apply to those tags through the tag hierarchy as for the other helmets. I did not
verify this against a live game hit.

## Not determined

- Live confirmation. Nothing here was observed in the running game; all values are derived from data
  and the documented rule.
- Whether Ghillie context tags matter for any rule entry (they have R = 0 in the item data and no
  coverage, so they do not change the result through the armor rule).
- Slot exclusivity (inference 2 above).
- Mounted weapons, vehicle weapons and explosive sources are out of scope, as in round 24. For
  explosives, round 8 shows the general armor hook with empty location input accepts every equipped
  piece and skips the coverage test, so coverage by location does not apply there.

## Where the armor rule differs per location

The rule itself is the same at every location: covering piece kept, R scaled by the ammo scalar. What
differs is which items pass the coverage test. The only structural differences found are:

1. Neck: covered by Heavy, SuperHeavy and Tank helmets but not by Light, Medium or Pilot helmets.
2. Pelvis and Arm.Upper: covered by the SuperHeavy vest only.
3. Direct projectile hits use the hit bone to restrict coverage; radial and back-blast hooks supply no
   location and accept every equipped piece (round 8). This tool models direct bullet hits only.

## Largest changes against the old "unarmored" assumption

Round 24 showed Neck, Torso.Middle, Arm.Upper and others as unarmored. For an armored target the
real value is lower by the factors above. For M4 FMJ: Neck 49.4 becomes 24.7 (Heavy), 22.2 (Tank)
or 19.7 (SuperHeavy); Torso.Middle 27.2 becomes 19.0, 16.3, 13.6 or 10.9 for Light, Medium, Heavy
or SuperHeavy; Pelvis 25.2 becomes 10.1 and Arm.Upper 15.1 becomes 6.0 under SuperHeavy. The
largest absolute drop is the SR_04 hollow point at the Neck (486.1 unarmored; 7.0 into a SuperHeavy
helmet, 15.3 into Tank, 19.7 into Heavy), because hollow point is strongly penalized against armor.
Armor piercing narrows the gap: M4 AP Neck 39.5 becomes 27.6 (Heavy) or 25.3 (SuperHeavy).
