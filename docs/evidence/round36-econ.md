# Round 36: where the economy and progression "not yet known" values live

Seven gaps on the wiki's Progression and Economy pages. For each: status (FOUND, NATIVE, SERVER, ABSENT), values, source, evidence level and how to reproduce. Everything is static: cooked data read with the offline extractor, SDK headers, and string and pseudocode search. Nothing was run or contacted.

| # | Gap | Status |
|---|---|---|
| 1 | Weapon (platform) mastery: XP, levels, rewards | ABSENT in the client; no backend type for it either |
| 2 | Achievements: thresholds and rewards | FOUND (4 thresholds, criteria for all 10); rewards ABSENT (a Steam achievement is the only reward) |
| 3 | Wagers: targets and payouts | FOUND (counts, odds, limits); settlement is SERVER |
| 4 | Skill unlock level or cost, skill points | ABSENT in the client (skills are not in any unlock table; skill points are reserved tags only) |
| 5 | Gold Bars and Intel | Gold Bars: FOUND route (cash exchange), rate SERVER. Intel spending: ABSENT |
| 6 | Season routes, MH-6 expiry | Schedule SERVER; routes FOUND (Gold Market and order fulfilment only); expiry enforcement unresolved |
| 7 | Mastery rewards per role level | FOUND: the `Rewards` arrays are empty; the unlock tree is the reward |

Machine-readable rows: [`assets/data/economy.json`](../../assets/data/economy.json), written by [`_tools/economy_tables.py`](../../_tools/economy_tables.py).

## The backend serves these tables (the SERVER question, answered once)

Evidence level: SDK headers (`sdk/raw`), static.

- The client links the Pragma Engine backend SDK (`PragmaSDK`, `OnlineSubsystemPragma`). Player state is requested through proto structs: `Pragma_PlayerData_CreditCurrency*`, `TryDebitCurrencies*`, `PurchaseCollectionItem*`, `GrantCollectionItems*`, `GrantFulfilledCollectionItems*`, `ExecuteExchange*` and `ExecuteExchangeV2*`, `GetGoldExchangeState*`, `UpgradeNode*`, `UpdateNode*`, `CurrenciesHandleSeasonReset*`, `PlayerMasteryHandleSeasonReset*`, `TrySeasonReset*`, `ForceSeasonReset*`, and `Pragma_Order_*` (Steam inventory and ownership, Epic entitlement, Xbox, PlayStation and Twitch order sources).
- Game content reaches the client as versioned "game data": `EPragma_CustomGameData_DataArray_TypeType` has 18 types: GlobalAnnouncements, Currencies, PlayerMastery, VendorData, ExchangeDefinitions, LiveCurves, ChallengeRewards, MetaTrees, GoldMarketItems, Collection, Seasons, MockInvestments, ClientHotConfig, WagerActions, WagerConditions, WagerPricing, WagerObjectiveCatalog. `GetVersionedGameDataV8Response` carries the first fourteen. Each has a client marshaler (`UOnline*DataMarshaler`) and a `UWD*BackendDataHandler`.
- `UBackendGameDataExporterConfigurationPragma` lists the file paths the editor exports for each type (currency, exchange, gold market, mastery, meta trees, vendor, live curves, challenge rewards, season definitions, vault entries, mock investments, client hot config, four wager files). The cooked client tables ([`DT_CurrenciesDefinitions`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/CurrencyDefinitions/DT_CurrenciesDefinitions.json), [`DT_ExchangeDefinitions`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/ExchangeDefinitions/DT_ExchangeDefinitions.json), [`DT_GoldMarket`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/Collection/DT_GoldMarket.json), [`DT_RoleMasteryDefinitions`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/Levels/Roles/DT_RoleMasteryDefinitions.json), [`DT_MetaTree_Roles`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/CharacterSkills/DT_MetaTree_Roles.json), [`DT_SeasonDefinitions`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/DT_SeasonDefinitions.json), `DT_Wager*` and so on) are the source of those exports. What the live service holds today can differ; this repository sees only the shipped copy.
- Types that do not exist as content: there is no platform mastery, achievement, skill point or Intel content type. That is the evidence behind the ABSENT results below.

## 1. Weapon (platform) mastery

Status: ABSENT. Evidence: cooked data read, SDK headers, tag lists. Not run.

- Membership is known. [`DA_UI_PlatformMastery_SceneData`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/UI/Features/Frontend/Mastery/Platforms/Data/DA_UI_PlatformMastery_SceneData.json) lists the platforms per type. Weapon Mastery: AssaultRifle 5 (AK74M, M4, KH2002, TAR21, A91), LMG 2 (LMG_02 = PKM, M249), MarksmanRifle 3 (RFB, SKS, SVDM), Shotgun 2 (MP43, M500), SMG 3 (MP9, Vector, SMG_03), Sniper 4 (MK22, SV98, Mosin, SR_04), Pistol 2 (Glock17, Judge), Launcher 4 (RPG7, CGM4, Launcher_04, MMGL): 25 weapons. Vehicle Mastery: LandVehicle 5 (Artillery, Heavy tank, Kodiak, Bobcat, Lonestar spawn vehicle), AirVehicle 3 (Havoc, Littlebird, ROT_01): 8 vehicles. The wiki says eight types of weapon; it does not mention the vehicle half or the exact weapon lists (they differ from the wiki's class lists: for example no Galil, FAL, Bushmaster, Evo-3 Ultra).
- No XP per level, no max level, no reward per level. `DA_UI_PlatformMastery_*` hold colours, icon tags and text only. The classes behind them (`WDUIPlatformMasteryProgressViewModel`, `...ProgressBarViewModel`, `...RewardViewModel`, `...RewardData`) are UI types.
- The XP plumbing is reserved but unused. `Attribute.Meta.XP.Platform.*` exists for 26 weapons ([`WEPN_001`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Plugins/GameFeatures/Weapons/Platforms/WEPN_001/Content/WEPN_001.json) to [`WEPN_026`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Plugins/GameFeatures/Weapons/Platforms/WEPN_026/Content/WEPN_026.json)) and 8 vehicles (Bobcat, Havoc, Huey, Kodiak, Leopard, LittleBird, PZH2000, SpawnVehicle). `GE_Meta_ResourceChange` has one SetByCaller Add modifier for each. But `PlatformXPTag` (a field of `BHEntityData_UI`) is `None` on all 628 entity-data rows in every `DT_EntityData_*` table, no reward or challenge row names a platform XP tag, and [`DT_RoleMasteryDefinitions`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/Levels/Roles/DT_RoleMasteryDefinitions.json) has only the six roles. The native tag `Attribute.Meta.XP.Platform` is registered at RVA 0x128B310 (`sub_14128B310`, `AddNativeGameplayTag`); that is a registration, not an award rule.
- Skins carry a mastery colour. Each skin asset ([`Skin_BlackAndGold`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Plugins/GameFeatures/Skins/Season01_SkinsData/Content/Data/Skin_BlackAndGold.json), [`Skin_DigitalWood`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Plugins/GameFeatures/Skins/Season01_SkinsData/Content/Data/Skin_DigitalWood.json), ...) has `MasteryColour` and `DisplayMastery` (0 or 1) per weapon, so a mastery-coloured part is a planned cosmetic. When it shows is not in the data.
- How XP is earned and what each level gives: not determinable from the client. The backend has no platform mastery content type, so there is nothing to ask for. The Season 1 skins are bought on the Gold Market, not earned.

Reproduce: `python -I _tools/economy_tables.py` (`platformMastery`); `grep -rl "XP.Platform" data` finds only the tag list; entity rows with `PlatformXPTag` set: 0 of 628.

## 2. Achievements

Status: thresholds FOUND, rewards ABSENT. Evidence: cooked package bytes read (thresholds), StateTree export read (criteria).

The achievement rows ([`DT_Challenges_SessionEvents_Shared`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/Challenges/DT_Challenges_SessionEvents_Shared.json)) have `Rewards` `[]` and `Objectives` `[]`; [`DT_Achievements`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/Achievements/DT_Achievements.json) has only the Steam id and name. The reward of an achievement is the Steam achievement itself.

| Achievement | Steam id | Threshold | Criterion |
|---|---|---|---|
| Loadout Spender | `ACH_ECONOMY_LOADOUT_SPEND` | `CashThreshold` 100,000 | One loadout purchase event (resource = cash) with a change of at least 100,000 (`GreaterOrEqual`). Sign handling of the change is not read. |
| Single Life Profit | `ACH_ECONOMY_SINGLE_LIFE_PROFIT` | `CashThreshold` 100,000 | The match-stat profit difference reaches 100,000 (`GreaterOrEqual`) on a profit-changed event. |
| Control Zone Survivor | `ACH_SURVIVAL_CONTROL_ZONE_SURVIVOR` | `RequiredSeconds` 3,600 (1 hour) | Enter a control zone, then stay (alive) for 3,600 s; a death resets the watch. |
| Long Shot | `ACH_COMBAT_LONG_SHOT` | `DistanceThreshold` 95,000 (Unreal units, cm: 950 m) | A kill of a hostile target at message distance at least 95,000 (`GreaterOrEqual`). The unit is derived: the kill-distance reward curves use the same unit (30,000 = 300 m). |
| Complete The Tutorial | `ACH_TUTORIAL_COMPLETED` | none | `Event.StateTree.TutorialCompleted`. |
| Punch Kristopher | `ACH_TUTORIAL_PUNCH_KRISTOPHER` | none | Melee damage to the tutorial NPC Kristopher. |
| Top Cash Earner | `ACH_ECONOMY_TOP_CASH_EARNER` | none | No event; a match-stat check: cash-earned placement is 1 and cash earned is above 0. |
| Ricochet Kill | `ACH_COMBAT_RICOCHET_KILL` | none | Kill of a hostile with the ricochet tag. |
| Defibrillator Kill | `ACH_COMBAT_DEFIBRILLATOR_KILL` | none | Kill of a hostile with the defibrillator tag. |
| Clean Sweep | `ACH_MATCH_CLEAN_SWEEP` | none | Final faction scores: own score above 0 and the opposing faction at 0. |

"Hidden criteria" in the sense of conditions the name does not state: Top Cash Earner needs a positive amount as well as first place; Clean Sweep needs the player's own faction to have scored; Control Zone Survivor is lost on death; Punch Kristopher needs melee damage; Long Shot, Ricochet Kill and Defibrillator Kill only count hostile targets. The Steam ids are in [`DT_Achievements`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/Achievements/DT_Achievements.json) and in `economy.json`.

### How the bytes were read

CUE4Parse exports a property bag (`Parameters`) as descriptors and `SerialSize` and skips the values, so the JSON in `data/` shows `SerialSize` 6 and 3 but no number. `docs/evidence/round36-econ-package-bytes.cs` dumps a package's bytes. In [`Meta/Challenges/DT_Challenges_SessionEvents_Shared`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/Challenges/DT_Challenges_SessionEvents_Shared.json) each override is: descriptor GUID, name, value type, `int32 SerialSize` = 6, then an unversioned-property block: a 2-byte fragment header (`00 03` = one value, no zero mask) and the 4-byte value:

| Parameter | Block | Value |
|---|---|---|
| Loadout Spender `CashThreshold` | `00 03 a0 86 01 00` | int32 100000 |
| Single Life Profit `CashThreshold` | `00 03 a0 86 01 00` | int32 100000 |
| Control Zone Survivor `RequiredSeconds` | `00 03 00 00 61 45` | float 3600.0 |
| Long Shot `DistanceThreshold` | `00 03 00 8c b9 47` | float 95000.0 |

Method check: the same decoding of [`DT_PassiveMissionChallenges`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/Missions/DT_PassiveMissionChallenges.json) EarnCash.1 (bag `SerialSize` 31, header `00 07`, first value `88 13 00 00`) gives `RequiredAmount` 5000, equal to that row's objective value 5000. The tutorial and other achievements have `SerialSize` 2 (no parameters). `python -I _tools/economy_tables.py --bytes <dir>` re-checks these against a dump.

## 3. Wagers

Status: counts, odds and limits FOUND; settlement SERVER. Evidence: cooked data read (plus UI strings for the formula).

- Targets. The four wager challenges ([`DT_WagerChallenges`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/Wagers/DT_WagerChallenges.json)) hold only a placeholder: the bag value of `NumPlayersToKill` is 1 (bytes `00 03 01 00 00 00`). The target is the count the player picks. [`DT_WagerActions`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/Wagers/DT_WagerActions.json) gives each action's range and default:

| Action | Count (min to max, default) | Cooldown | Rules |
|---|---|---|---|
| Kills | 1 to 25, default 1 | 86,400 s | Inside the control zone; enemy players only; not a player an enemy revived; repeats on the same player do not count |
| PlayerDelivery | 1 to 20, default 1 | 86,400 s | Spawn vehicles do not count; counts once the passenger survives the drop-off |
| Revives | 1 to 50, default 5 | 86,400 s | Inside the control zone; teammates only; not a player downed by a teammate or themselves; repeats on the same player do not count |
| VehiclesDestroyed | 1 to 20, default 1 | 86,400 s | An enemy must be driving it; an enemy must have bought it |

- Odds by count. Each action has an odds list indexed by count. Kills: 1.001 for counts 1 to 3, 1.0055 at 4, 1.01 at 5, up to 1.2004 at 25. Revives: 1.001 to count 5, up to 1.2498 at 50. PlayerDelivery: 1.001 to count 5, 1.0771 at 20. VehiclesDestroyed: 1.001 to count 3, 1.1479 at 20 (full lists in `economy.json`).
- Pricing ([`DT_WagerPricing`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/Wagers/DT_WagerPricing.json)): stake 2,500 to 100,000 cash, `MaxPayout` 5,000,000, `FoldBonusStep` 0.25, `LivesOdds` [1.009, 1.003, 1.002, 1.001], two unnamed floats 1.001 and 100.0.
- Conditions ([`DT_WagerConditions`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/Wagers/DT_WagerConditions.json)): 50, each with an odds multiplier, from 1.005 (5 tapes in the vehicle) to 10.0 (Deathwish); others include Time Limit 4.0, No Vehicles 3.0, No Resupply 2.0, Havoc destroyed 1.7, With Headshot 1.2.
- Prebuilt objectives ([`DT_WagerObjectiveCatalog`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/Wagers/DT_WagerObjectiveCatalog.json)): 17. Public ones: Kills3 (3 kills, 1.001), Kills2WithHeadshot (2, 1.2012), Revives2 (2, 1.001), PlayerDelivery3 (3, 1.001), VehiclesDestroyed1 (1, 1.001). Three are test rows (`TestParked` 300 s cooldown, `TestLockedWagerNode`, `TestLockedNodeInNoTree`). Nine carry the flag set (Hammertime 10/20/25 kills at 1.5/1.64/1.72 in a hot zone with a hammer; MedicMarathon 30/40/50 revives at 1.37/1.44/1.51; AllDrillerNoFiller 15/20/25 kills with the light drill at 1.57/1.64/1.72).
- Slip rules from the UI text ([`DA_VendorPanel_Wagers_Create`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/UI/Features/Vendor/Widgets/VendorPanel/Data/DA_VendorPanel_Wagers_Create.json), [`DA_WagerReceipt`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/UI/Features/Wagers/Receipt/DA_WagerReceipt.json)): "Every objective after the first adds x{Step}" and "{Legs} objectives: 1 + {Extra} x {Step}" (so a multi bonus of 1 + (objectives - 1) x 0.25), "Total odds", "Return", "{Line} (capped)", "Requires Wardog level {Level}", deaths allowed. The `LivesOdds` list is read as odds by deaths allowed; that is an inference from the strings.
- Not in the client: the exact settlement formula (stake times combined odds, capped at 5,000,000, is what the labels say) and the Wardog level that unlocks wagers. The unlock tag `Meta.Unlocks.Wager` is named by a test objective but is not a node in [`DT_MetaTree_Roles`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/CharacterSkills/DT_MetaTree_Roles.json). Wager pricing, actions, conditions and the objective catalog are four exported backend content types, so settlement is a backend operation (status SERVER; formula not read).

## 4. Skill unlocks and skill points

Status: ABSENT. Evidence: cooked data read, SDK structs, tag lists.

- [`DT_MetaTree_Roles`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/CharacterSkills/DT_MetaTree_Roles.json) is the only `WDMetaTreeTableRow` table. Its 264 nodes (7 trees: six roles and Wardog) are items and vehicles and the Gold Exchange; every node has one level, one level gate and a cash cost. None of the 62 skill tags is a node (checked by tag).
- The tree UI layout ([`DA_UI_RoleSkillTree_NodePresetData`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/UI/Features/Frontend/Mastery/Roles/Data/DA_UI_RoleSkillTree_NodePresetData.json)) places 130 nodes (Infantry 29, Medic 22, Support 27, Pilot 12, Recon 28, Driver 12), a circular grid of 4 rows by 9 columns. Only 62 have an effect row (`DT_*Skills`). The other 68 have a name and description in [`DT_CharacterSkillNodes_Data`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/UI/Data/DT_CharacterSkillNodes_Data.json) (131 rows) and a grid position only, for example `Meta.Role.Infantry.StrongArm`, `Meta.Role.Infantry.MeleeDamage`, `Meta.Role.Medic.DragSpeed`, `Meta.Role.Support.ReloadSpeed.LMG`.
- The upgrade call: `WDMetaTreeComponent::Server_TryUpgradeNode(treetag, NodeTag)` and `Pragma_PlayerData_UpgradeNodeRequestProto` (NodeId, TreeId, MetaTrees, Currency and PlayerMastery content versions). The backend checks the exported tree, which has no skill node.
- Skill points: six `Attribute.Meta.Currency.SkillPoint.Role.<Role>` tags and six SetByCaller Add modifiers in `GE_Meta_ResourceChange`, beside the role XP modifiers. [`DT_CurrenciesDefinitions`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/CurrencyDefinitions/DT_CurrenciesDefinitions.json) defines only Cash and Gold Bars (a `Pragma_Content_CurrencySpec` is built from it), no table or reward row grants skill points, and the tag has no other use in `data/` or the SDK. So skill points are reserved: no earning rule and no cost in the client.
- What the skill rows do carry: the curve of values by rank (see [Progression](../../game-features/Wardogs_Progression_v1.md)). Rank thresholds, if any, are not in the client.

## 5. Gold Bars and Intel

Status: Gold Bars route FOUND, rate SERVER; Intel spend ABSENT. Evidence: cooked UI text, SDK structs, static.

- Gold Bars are earned by exchange, not by play. The Gold Exchange text ([`DA_InfoPrompt_GoldExchange`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/UI/Features/Frontend/GoldExchange/Data/DA_InfoPrompt_GoldExchange.json)): "Exchange cash earned in matches for Gold Bars - WARDOGS endgame currency. Gold bars can then be used to obtain cosmetics in the Gold Market. Exchange rates of gold vary so timing your exchange is key... Gold Bars exchanges cannot be resold / refunded." The unlock node text says "Trade cash for gold bars which can be used to unlock cosmetics". The progression info prompt adds: "At the end of a major update cycle your level progression and cash will be reset... Any remaining cash at the end of a cycle will be automatically exchanged for gold bars."
- The exchange is gated: `Meta.Unlocks.GoldExchange` in the Wardog tree needs Wardog level 35 and 150,000 cash.
- The rate is server data. [`DT_ExchangeDefinitions`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/ExchangeDefinitions/DT_ExchangeDefinitions.json) has a Gold Bars row with `ExchangeRates` `[]`. The backend type `Pragma_Content_ExchangeDefinitionSpec` is an ExchangeId with a `PriceHistory`; the graph widget has 1W, 4W, 12W and 52W ranges and the label "{ExchangeRate} = 1 gold bar". The requests carry the content version and a data timestamp (`ExecuteExchangeV2requestProto`: ExchangeId, Quantity, CurrencyContentVersion, ExchangeContentVersion, ExchangeDataTimestampSeconds). `GetGoldExchangeStateResponseProto` returns Enabled, UnlockNodeId and Unlocked.
- Season end: `CurrenciesHandleSeasonResetResponseProto` returns `EndOfSeasonCashValue` and `RewardedGoldBars`; `SeasonCompletedComponentProto` stores both with the end-of-season mastery info. So the leftover cash is converted by the backend at the reset. No cash-to-gold rate is in the client.
- Other earning paths: no reward row, challenge, mission or achievement pays Gold Bars (`Attribute.Meta.Currency.GoldBars` appears 5 times in `data/`: twice in the currency table, twice in the exchange table, once in the Gold Exchange graph). The order service (`Pragma_Order_*`, with Steam inventory, ownership and other storefront sources, and `bEnableFulfillOrders=True` in [`DT_ClientHotConfigs`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/ClientHotConfigs/DT_ClientHotConfigs.json)) exists, but no SKU or Gold Bars pack is in the client, so whether Gold Bars are sold for money is not determinable. Currency spec also has a `Limit` field; the client table sets none.
- Intel. `Attribute.Meta.Currency.Intel` appears 15 times in `data/`, all as the reward of the 15 passive mission tiers (100 to 500; reward type `REWARD_TYPE_INVALID`). It is not in [`DT_CurrenciesDefinitions`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/CurrencyDefinitions/DT_CurrenciesDefinitions.json) (so no starting balance, no backend currency spec), is in no cost list (every one of 264 unlock costs and the investment costs is cash), no vendor or exchange uses it, and the Black Market missions panel ([`DA_MissionsPanel_Intel`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/UI/Features/Frontend/BlackMarket/Missions/Widgets/Panels/Data/DA_MissionsPanel_Intel.json)) only lists the missions. Intel has no spend path in the client. The native tag list (`Attribute.Meta.Currency.Cash`, `.Intel`, `.GoldBars`) shows it is a known currency tag.

## 6. Seasons, cosmetic routes and MH-6 expiry

Status: schedule SERVER; routes FOUND; MH-6 expiry enforcement unresolved. Evidence: cooked data, SDK, static.

- Schedule. [`DT_SeasonDefinitions`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/DT_SeasonDefinitions.json) is `CurrentSeasonNumber` 1 with an empty list. The backend season type is `Pragma_Content_SeasonDefinition` (SeasonNumber, SeasonName, HasExpirationTime, ExpirationTimestampSeconds), delivered in game data. The season rewards popup reads "SEASON {SeasonName}" and a role level view model, and the progression scene shows a countdown ("{Days}:{Hours}:{Minutes}:{Seconds}"). So the real schedule (dates, names) is server-side and not visible.
- What a season does (UI text and backend structs): progression (levels and cash) resets at the end of a major update cycle with notice; remaining cash is exchanged for Gold Bars; end-of-season mastery info is stored.
- Reward tracks. There is no battle-pass content: no season reward track type exists among the 18 content types; the "reward track" widgets (`TreeRewardTrack*`) are the role unlock tree view. Season 1 and Season 2 cosmetic tables (`DT_Cosmetics_Season01_*`) are collection items with no level, cost or unlock field.
- Cosmetic routes in the client: (a) Gold Market purchase: `PurchaseCollectionItem` with a Gold Market price (`GoldMarketItemSpec`: cost, tile, expiry); (b) backend grants: `GrantCollectionItems` and `GrantFulfilledCollectionItems` (fulfilled items come from the order service, with `AvailableOn`, per platform). Items with no Gold Market row (AK74 Black and Gold, faction logos, taxi skin, bobbleheads) can only come from route (b) or something outside the client; which one is not determinable.
- MH-6 (Black and Gold Little Bird, `Meta.Cosmetic.BlackAndGold.Littlebird`): 30 Gold Bars, `ExpirationType` `EXPIRATION_NO_END_TIME` (value 1), `ExpirationTime` 639342720000000000 ticks = 2026-12-31 00:00:00 UTC. The enum has three values: NO_EXPIRATION (0, the other 26 rows), EXPIRATION_NO_END_TIME (1) and EXPIRATION_WITH_END_TIME (2); the backend spec has the same three and a timestamp. The Gold Market tile shows a "{Days}:{Hours}:{Minutes}:{Seconds}" countdown. No function that reads the expiration type was found in the pseudocode corpus (search for the field and type names gives nothing), so whether type 1 hides the item at the timestamp, or only flags it, is not determinable here. Type 2 would be the one that names an end time. Wiki wording should stay: flagged as expiring, date 31 Dec 2026 in the data, effect not confirmed.

## 7. Mastery rewards per role level

Status: FOUND (none are listed). Evidence: cooked data read.

- [`DT_RoleMasteryDefinitions`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/Levels/Roles/DT_RoleMasteryDefinitions.json) has 101 level rows (0 to 100) for each of the six roles, identical XP curves (level 100 needs 5,132,500; level 1 200, level 10 25,000), and an empty `Rewards` array on every one of the 606 rows. The backend `Pragma_Content_LevelDefinition` has a Rewards list and `Pragma_Content_Reward` types (unlock challenge, unlock component, currency), but the client table fills none.
- What a level does give is access: the unlock tree gates each item behind a role level and a cash price. Counts (nodes, level range, total cash): Recon 58 (2 to 50, 2,445,000), Infantry 40 (2 to 50, 1,270,000), Medic 38 (1 to 50, 1,220,000), Support 33 (1 to 50, 1,630,000), Driver 21 (3 to 35, 2,308,250), Pilot 11 (2 to 35, 1,218,250), and the Wardog tree 63 (1 to 150, 2,645,000). The Wardog tree runs to level 150, so the overall Wardog level is not capped at 100 like the role levels; how the six role levels combine ("all role levels culminate into your overall wardog level") is not shown. Free nodes (cash 0) are magazines and ammunition that come with a weapon.
- Per node rows are in `economy.json` (`roleUnlocks.nodes`: tree, tag, name where the item name is known, level, cash). 191 of 264 tags have no friendly name in the entity tables, so they stay as tags.
