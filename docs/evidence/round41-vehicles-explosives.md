## A. The four worked-but-open items

### R41-1 Engine restart while the tank is empty. FOUND (static disassembly)

Chain: `Server_StartEngine` -> slot 283 -> slot 302 refuses when slot 300 (`0x53CB360`, shared by every vehicle pawn class) says no. Slot 300 calls pawn slot 316 (`0x76BB690`, returns the `UWDVehicleGameplaySystemsComponent` at `pawn+0xBF0`); when that is null or being destroyed it returns **true**, otherwise it tail-calls the component's virtual `+0x530` (slot 166). The component's slot 166 is **`0x767B600`**: it fetches the fuel component (`0x76697A0`) and calls **`0x7666030`**, which is the body of `GetVehicleHasFuel` (the reflected thunk `0x7667660` has the identical logic): it returns true when the byte `+0xB8` of the fuel component has its sign bit set (a flag whose name was not mapped; it makes the check pass regardless of fuel), otherwise true only if the fuel attribute (`+0x138`, read through `0x52301F0`) is **greater than 0.0**; with no fuel component it returns false. So **an engine cannot be started again while the tank is empty**; it can after refuelling (the stop itself is R40-1). The base class slot (`0xD356F0`) is `return true`, which is why vehicles without the WD component are unaffected.

### R41-8 Refuel Max early stop. FOUND (static disassembly)

`Server_RequestRefuelOrRepair` (`0x85D5C80`) -> `UWDPawnBuildableManager` slot 162 (`0x85CC230`) -> **`0x85EEB80`**. Gates: the pawn is the authority (`+368 == 3`), the station tag equals one of two global tags (refuel or repair), the speed index selects a table row. Let `pool` = the vehicle's maximum fuel (kind 0) or maximum health (kind 1) (`0x7666010` / `0x7665F90`, `0x7679A50`), `have` = how many of the row's supply item the FOB holds, `cost` = the row's integer item cost (record `+0x44`). Then:

- `fullCost = max(cost * pool, 1)`; `amount = min(have / fullCost, 1) * pool` (limited by the FOB's supplies);
- `amount = min(amount, pool_max - current)` (limited by what is missing; fuel via `0x7666010 - 0x7665F90`, health via `0x7679A50` pair);
- `fraction = amount / max(pool, 1)`;
- supplies charged = `round(cost * amount)` (computed as `-(int)(-0.5 - 2*fullCost*fraction) >> 1`), removed from the FOB inventory;
- cash charged = `50 * ceil(round(MoneyCost * fraction * 0.04) / 2)`, i.e. the row's money cost scaled by the fraction and **rounded up to a multiple of 50**.

So **a Max restock stops early in cost terms**: you pay only for the share you actually receive (a nearly full tank costs little), and you cannot receive more than the FOB can supply. The charge is taken at the request; a record (80 bytes: amount `+24`, supply count `+28`, ...) is created and the restock completes after the stored restock time (round 36: Max 9 s). Whether `Server_RequestCancelResourcesTaken` refunds the unused share was not read (NATIVE, small).

## C. The ten explosive items

### R41-14 Fire field end at 45 s against the ubergraph timer. FOUND (Blueprint bytecode + static)

The fire field and its trigger volume have `InitialLifeSpan` 45.0 (round 8): that is when the actors are destroyed. The "later one-shot timer" in `ExecuteUbergraph_B_Molotov_FireField` (set in `ReceiveBeginPlay`) is `K2_SetTimerDelegate` with time **`GetPatchDuration() - 3.0`**; the dump does not show the delegate target, but the only audio-stop request in the graph apart from `ReceiveEndPlay` is `Audio.Event.Weapon.Throwable.Molotov.Burn.Stop`, sent just before the begin-play node. Fire field constructor `0x86A0140`: `+0x2D0` 250.0 (Blueprint sets 2,000), `+0x2D4` 600.0, `+0x2D8` 150.0, `+0x2DC` 4.

### R41-17 Downstream friendly-fire rules. FOUND (cooked data, all tables)

Across **every** `DT_GlobalDamage_*` table (infantry, armor, vehicle and its per-vehicle files, buildables) exactly two entries require an alignment: [`DT_GlobalDamage_InfantryData`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/GameMechanics/DamageSystem/DamageDataTables/DT_GlobalDamage_InfantryData.json) `Meta.Damage.Infantry` with `AlignmentRequired = Friendly`: `Meta.Damage.Bullet` -50 % and `Meta.Damage.Utility.LargeHammer` -70 %. ### R41-20 Throw-velocity curve combination. FOUND (Blueprint bytecode, order of operations)

`B_Action_ThrowExplosive` -> `CalculateLaunchParams` calls `CalculateThrowLinearVelocity`, `CalculateThrowAngularVelocity`. **Direction** (`CalculateThrowDirection`): the controller's pitch is clamped to -90..90 and mapped through a float curve (`MapRangeClamped` -90..90 onto -90..90) to give the launch pitch, then `RotatorToVector`. **Linear velocity**: the owner's velocity (`GetVelocity`) is split into horizontal and vertical parts, each multiplied by its influence value clamped with `FMin(..., 1.0)` (data: "owner velocity influence vertical / horizontal"); the throw's own speed is the throw action's velocity (cm/s) scaled by a second `CurveFloat:GetFloatValue` of the clamped view pitch (the `CRV_ThrowVelocity_*` curve) unless "constant velocity" is set; the two vectors are added (`Add_VectorVector`). **Angular velocity**: random in the min..max range per axis from a random stream. Exact multiply order inside one expression was not traced statement by statement.

### R41-21 `MinimumRemainingFuseTime`. FOUND (static disassembly)

`FWDGrenadeInteractionData` = {`MaximumVelocity` 250.0, `MinimumLifetime` 0.5, `SphereRadius` 25.0, `MinimumRemainingFuseTime` 0.0} (native defaults, `AWDGrenade +0x640`); the grenade copies the block to its throw-back interaction context (`0x6CAE470`, context `+0x1A0`). The eligibility check **`0x6CAE290`** passes only when: the grenade's age (server time minus its spawn time `+0x654`) is **greater than MinimumLifetime**; the grenade's speed (`GetVelocity`) is **not above MaximumVelocity**; and the fuse timer's remaining time (`0x6CAE830`, timer handle `+0x658`, remaining = expire time minus now) is **greater than MinimumRemainingFuseTime**. `B_FragGrenade` sets `MinimumRemainingFuseTime` to **5.0** while its fuse is 4.0 s, started with a duration read from the grenade's fuse component (`0x6CAF180`: field `+0x368` minus `+0x398`, taken to be the base fuse minus the cooked time): by this static reading the remaining time can never exceed 5.0, so **the gate cannot pass for the M67 as shipped** even though `bCanThrowBack` is true. This conflicts with the wiki's "can be thrown back"; it needs an in-game check (not done, the game is never run).
