### R42-1 Flares against missile lock-on. ABSENT (searched); restock source NATIVE (small)

What a flare does in the code that was read: the client-side fire handler (`0x766EDF0`, vehicle gameplay-systems component, runs when the local role is not authority) requires the cooldown flag (`+0x798`) and a flare count (`+0x790`), sets `bFlaresActive` (`+0x791`), stores the activation time in the float at `+0x794`, and starts two timers (rates from `+0x2D4`/`+0x2D8` of the settings copy, i.e. the active window and the cooldown); the timer callbacks `0x76794B0` (clears active) and `0x7679520` (sets cooldown reached) are the only users. The visual is the gameplay cue `GC_Vehicle_Flares`, placed at the location sent by `Client_SetFlaresActivatedLocation` (`0x7689520`).

Why no lock interaction is found (all negative, so a bounded ABSENT, not a proof):

1. **Both lock-on Blueprints are clean.** `B_Action_Ads` and `B_Action_Vehicle_Weapon_Ads` (the `WDAction_Ads` subclasses that run the lock progress, `OnTargetLockAcquired/Lost/Progress`) contain no reference to a flare, countermeasure, smoke or threat name. Their `BP_CanTarget` only compares the target against `TargetingHardDeckLimit` and the weapon stats (`GetWeaponStats`); `TargetUnderHeightThreshold` is a height test.
2. **The native target manager does not ask the target about flares.** `0x6A68DF0` (16 KB; the `WDLockOnTargets` accumulator with the lock-progress map, called from `0x6A68A30`) calls only the lock-list helpers (`0x7670BB0` remove, `0x6A66A60` add, `0x7668260` class getter), map helpers and its own small helpers. Its time test compares accumulated lock time with a float of the weapon's targeting settings (`+0x98`). No call into the vehicle component's flare getters, and no read of `+0x790..0x798`.
3. **`bFlaresActive` has UI readers only** (round 41: getter `0x767A0B0`, called by the view-model proxies). The flare range pair (`+0x2CC`/`+0x2D0` of the component's copy) has no reader outside the settings copy.
4. **Callers of the lock-list remove paths** (`0x7670DC0`, `0x7670BB0`, `0x766E620`, `0x766E900`) are: `0x6A66A60`, `0x6A66BF0`, `0x6A68DF0` (lock-on manager) and the rotary-vehicle virtuals `0x76B5CA0` / `0x76B7EE0` (slots 399 and 400, seat or weapon owner changes) and `0x76CEDB0`. None is the flare handler.
5. **The homing step is an interface thunk.** `SetHomingTarget` (`0x6C2C600`) is the `IWDWeaponOwner` thunk (no direct callers); the homing target itself is a scene component handed to the projectile. Nothing found lets a flare replace it.

So the data and code read show flares as a replicated count, cooldown and visual cue, with **no lock-clearing or lock-breaking path**. A seeker-side rule inside the projectile class could still exist (the missile projectile tick was not located). Restock: `Client_FlaresRestocked` (`0x4DD6400`) is only a thunk to component virtual `+0x558`; the count is replicated (`OnRep_UpdateFlareCount`) and no byte store to `+0x790` exists in the 0x6000000 to 0x7800000 range except an unrelated frame at `0x6D4E643`, so the server sets the count through a struct copy or another path. A `UWDVehicleWeaponRestockInteractionContext` and the garage "quick restock" UI exist; whether flares restock through them was not traced. **NATIVE next step (small):** break on writes to the component's `+0x790` during a garage or FOB restock, or locate the missile projectile tick (the class whose constructor stores `HomingTarget` at `+0x380`).

### R42-2 `MassOverride` units. FOUND (static disassembly + cooked data)

The consumer is **`0x531D520`**, the body initialiser of the airplane/helicopter vehicle component (data asset pointer at `component +0x488`, caller `0x531AF40`). It applies the asset field by field: inertia tensor (`+0x30`), inertia conditioning (`+0x50`/`+0x51`), then `if (asset->bEnableMassOverride [+0x52]) setMass(body, (float)asset->MassOverride [+0x58])`, then centre of mass (`+0x60`), linear damping (`+0x80`), angular damping (`+0x90`) and so on. The setter `0x24718B0` takes the float, widens it back to a double and stores it in the physics particle's mass field (`+0xF8`) and recomputes the inverse-mass field (`+0x138`). **There is no multiplier**: the cooked number goes straight to the engine, whose mass unit is kilograms (`SetMassOverrideInKg`). The setter is identified by what it writes, not by a symbol.

Values (5 assets, all enabled): FWG_01 body **10,000**; ROT_02 **7,500**; ROT_03 and ROT_03 RocketPods **722**; ROT_04 **9,500** (kg). Section 7 of the data page and `assets/data/air-vehicle-mass-override.json`. Not covered: the wheeled `Characteristics.Mass` (250 to 10,000, Humvee 7,250) goes through a different path that was not read, so its unit is still not shown by this evidence.

### R42-3 `GE_Vehicle_Health` consumers. FOUND (cooked data + static disassembly)

The effect is applied through the **driver and pilot skill "Increased supply crate durability"**, not to a vehicle's own health.

- Data: `Meta.Role.Driver.IncreasedHealth.SupplyCrate` ([`DT_DriverSkills`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/CharacterSkills/DT_DriverSkills.json)) and `Meta.Role.Pilot.IncreasedHealth.SupplyCrate` ([`DT_PilotSkills`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/CharacterSkills/DT_PilotSkills.json)) each hold one skill-effect group keyed by the slot tag **`Meta.Skill.SupplyCrate`**, effect `GE_Vehicle_Health`, with the custom magnitude `Attribute.Gameplay.Health` read from the curve row `IncreasedHealth_SupplyCrate` of [`CT_DriverSkills`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/CharacterSkills/CT_DriverSkills.json) / [`CT_PilotSkills`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/data/Wardogs/Content/Meta/CharacterSkills/CT_PilotSkills.json) (skill level 0: 1.0, 2: 1.2, 4: 1.4). Driver: `VehicleApplicationRequirements` `ANY(Vehicle.Variant.Land)`; Pilot: `ANY(Vehicle.Variant.Air)`. The effect multiplies health, so the supply crate dropped by a vehicle of that kind has 1.0, 1.2 or 1.4 times its health. The round 41 worry ("with no data it multiplies by 0") does not apply: the skill always supplies the coefficient. (Already listed in the [Progression page](../../game-features/Wardogs_Progression_v1.md), rows for both skills.)
- Native: the tag is a native tag, global `0xD36B3A0` (defined in the tag initialiser `0x128BB30`). Its only gameplay reader is **`AWDVehicleSupplyCrate` virtual slot 115 (`0x76304C0`, begin play)**: it takes the weak object at `crate +0x3C8` (the dropper), reaches its skill component (virtual `+0x738` with the skill-component class `0x69D9C00`) and registers a callback (`0x762EE40`) for the slot tag through `0x6CF3E30`. The callback walks the skill's effect groups (112-byte records) and applies each effect (`0x522B1B0`) to the crate's ability system component (`crate +0x328`) when the dropper is valid. So **it is applied when the crate is created (and again if the skill's effects change), for the player who dropped it**.

The vitality-helper callers listed in R41-12 (`0x52311D0`) are therefore unrelated to this effect.

### R42-4 Fire-field instigator. FOUND (static disassembly + Blueprint bytecode)

Chain, thrower to damage:

1. `B_Action_ThrowExplosive` (`ThrowOrExplodeExplosive`) assigns `SpawnedExplosive.Instigator = GetOwningPawn()` (statement 562) and calls `SetItemInstigatorPlayerState` on it: the thrown Molotov's `Instigator` is **the thrower's pawn**.
2. The Molotov explosion handler `0x86A15B0` builds the `FActorSpawnParameters` of the fire field with **Owner = the Molotov's `Owner` (`+0x160`)** and **Instigator = `GetInstigator()` of the Molotov** (`0x2FB5860`, returns `AActor +0x1A8`): decompiled stores `v236 = *(v6+352)`, `v237 = GetInstigator(v6)`, written into the params at +16 / +24 before `SpawnActor` (`0x4058990`). `SpawnActor` forwards them to `PostSpawnInitialize` (`0x3A9E6D0`), which stores the instigator in the new actor (`+0x1A8`) and calls `SetOwner` (virtual `+0x500`). So the fire field's `Instigator` is the thrower's pawn.
3. The Blueprint passes `Actor:GetInstigatorController` into `TryDamagePlayer` / `TryDamageVehicle`, which call `WDDamageSubsystem::SimpleDamageActorWithInstigatorController` (`0x6F09210`). That function puts the **instigator controller (and a state pointer read from it at `+0x2F8`) into the damage context** built by `0x6BB4D30`, together with the victim, the causer and the damage tag, and then runs the normal damage modification (`ModifyDamage`) and apply steps. A null controller does not stop the damage; the context is just built with an empty instigator.

Result: **fire damage is credited to the player who threw the Molotov**, and the instigator is in the damage context, so the alignment (friendly / hostile / neutral) logic of the [damage pipeline](../../pipelines/Wardogs_DamagePipeline_v2.md) can see it. What the tables do with that alignment is unchanged from R41-17: only infantry bullets (-50 %) and large hammers (-70 %) have friendly entries, so fire and explosives get no friendly-fire reduction from the tables. Not read: whether a global "friendly fire off" rule outside the tables exists, and what `GetInstigatorController` returns after the thrower dies (the pawn's controller reference is cleared when a pawn is unpossessed, so patches burning after the thrower's death may deal damage without an attacker; not traced).

### R42-5 M67 throw-back gate re-check. FOUND (static disassembly; confirms R41-21)

Direction of the comparison (`0x6CAE290`, raw bytes): after the age test (`comisd age, MinimumLifetime; jbe fail`) and the speed test (`comisd speed, MaximumVelocity; ja fail`), the remaining-fuse test is `call 0x6CAE830; comiss xmm0, [this+0x1AC]; jbe fail`. `jbe` jumps to failure when the remaining time is **less than or equal to** `MinimumRemainingFuseTime`; so it needs **remaining > MinimumRemainingFuseTime**, as stated in round 41 (`this+0x1AC` is the copy of `AWDGrenade +0x64C` made by `0x6CAE470` with one 16-byte move from `+0x640` to the context `+0x1A0`).

How the remaining time is measured: `0x6CAE830` returns 0.0 when the timer handle (`AWDGrenade +0x658`) is unset, otherwise the engine's timer-remaining for that handle. The handle is written in only one place, `StartFuseTimer` (`0x6CAF200`): it runs once (handle must be zero), only on the authority, and starts a timer of the length passed in. The launch-time caller `0x6CAF180` passes **`BaseFuseTime` (`+0x620`) minus the cooked time (`+0x650`)**, i.e. the full fuse for a fresh throw and less if the player cooked it; when the cooked time already equals or exceeds `BaseFuseTime`, `StartFuseTimer` takes a different branch (two virtual calls, read as the immediate detonation; not traced) instead of starting a timer. Hence the time left is **at most 4.0 s for the M67** and falls from there, while the gate needs more than 5.0. No other writer of `+0x64C`, `+0x1AC` (in this class family) or of the timer handle exists, the Blueprint sets `BaseFuseTime` 4.0 and `GrenadeInteractionData.MinimumRemainingFuseTime` 5.0, and `B_GoldFragGrenade` inherits both. **The gate cannot pass for the M67 or the Gold M67 as shipped, even though `bCanThrowBack` is true.** Molotov and smoke grenades keep the native `bCanThrowBack` false (the constructors `0x6CADC90` / `0x86A0200` do not set it), so they are not throw-back candidates at all.

Residual doubt, stated once: the identity of the "launch" event that calls `0x6CAF180` is inferred from its shape (an interface thunk at `this+0x2B8` with launch-parameter arguments), not named. A different start time would not change the bound: the fuse length is `BaseFuseTime` less the cook time. In-game confirmation is not possible under the project rules. Data: section 6 of the data page and `assets/data/grenade-throwback-gate.json`.
