# Gepard blast sampling: static control flow

Static CL-516586 executable review, 2026-10-19. This narrows [the Points-mode trace](round8-radial-points-components.md) for the Gepard (`VP_TNK_01_AntiAir`). Evidence is the offline restored executable SHA-256 `a5c3db107c29bfd92c3b5f317033f698a0c3a84dad712f32990ae302b4f0cc37`, its read-only decompilation corpus, the cooked platform/Blueprint exports and SDK. RVA ranges below were checked against original executable instructions. No game process or scene query was run.

## Candidate construction and order

For each overlapping component record, `6EFD9C0` calls the component's virtual slot `+0x598` at `6EFDA34–6EFDA4D`, passing component `+0x210` as the source of a 56-byte bounds result. `UStaticMeshComponent` uses slot target `3DB5AB0`. Its helper `44C2BA0–44C2BD0` copies `UStaticMesh::ExtendedBounds` at asset `+0x250` (`sdk/raw/Engine_classes.hpp:23489`); the bounds virtual can transform that authored bound. This is a component-calculated bounds origin, not the nearest displayed triangle or `RenderData.Bounds`.

The producer has a relevant branch, not a single unconditional sample rule. A positive overlap-record candidate count at `+0x38` sends the precomputed 96-byte sample records at `+0x30` through `6EFE759–6EFE8D8`. With zero such records, `6EFE8F5–6EFE9AE` seeds one 40-byte candidate from the returned bounds origin, recording squared distance to the **original blast origin** at candidate `+0x18`. A `UShapeComponent`-class branch at `6EFE9B7–6EFE9DD` can add further shape samples; ordinary static mesh components do not pass that class test. The 40-byte candidates are sorted ascending by that stored squared distance in `6EF4710` (comparator reads record `+0x18`) before `6EF7950` traverses them. At `6EF79E7–6EF7A36`, a positive `QueryPointEarlyRejectionDistance` (shipped initial 100 cm) skips candidates farther than `(ExplosiveRadius + rejectionDistance)^2` from the original origin. It is a candidate search gate, not the accepted-hit radius or damage falloff.

The precomputed count is material for Gepard. The producer `6EFFDC0` calls component vslot `+0x550` at `6F003FA`; the `UStaticMeshComponent` implementation `3DCD410` enumerates `UStaticMesh::Sockets` (asset `+0x200` pointer, `+0x208` count) and emits each socket's FName plus type byte 2. The global FName at `D380AE0` is initialized from ASCII `DamageQuerySocket` at `B433708` (`12DE0C0–12DE0CE`). At `6F00425–6F0042F` the producer compares the FName **comparison index**, so numbered instances of that base name match. When the overlap record's existing item-index list count at `+0x28` is zero, `6F00441–6F004E5` obtains the socket transform through vslot `+0x520` in mode 0 and appends a 96-byte record, incrementing count at record `+0x340`; the Points input at `6F0122E–6F0124E` receives that count as `+0x38`. The cooked `SM_TNK_03_*` rendered meshes have authored `DamageQuerySocket` entries; the viewer now uses all 89 transformed socket candidates, as recorded in the [integration report](round8-gepard-sampling-viewer.md). The earlier zero-count bounds branch remains a fallback for components with no accepted socket records. Record `+0x28` is subsequently populated with overlap `Item` indices (`6F0082F–6F00867`); it is not a socket-name filter.

The five relevant raw cooked exports are retained at `E:/Reverse_Engineer/wardogs_analysis/round8_gepard_explosive_collision_20261019/dump/`: `SM_TNK_03_Body.json` (59 matching sockets, SHA-256 `bb4b8f38e86f871be2e286944843da675672a11d64c3e0dc5b20390ab7ff365c`), `SM_TNK_03_Turret_Spin.json` (14, `6ee0fa5c01a058811957639cf2e782dd60333aba1617046793e051780c54b4fd`), `SM_TNK_03_Turret_Pitch.json` (10, `616c39a1df511a03e2550ac16f4bf99c7a0f84811624b2709b95a3756edffeb3`), and the left/right barrel JSON files (3 each, respectively `bc035141c480200ed822f57f38dac19029132c5b314939578798f8757415e87d` and `73ed8bfb25b5d7914bd9648369b23a7cd2f1d92abaf96a6c65f9f2565f8b3848`). These are the exported socket counts, not a claim that every candidate passes LOS or receives damage.

The important Gepard-specific continuation is easy to miss: `6EFD9C0` obtains the owner `WDDamageable` interface and calls its `+0x50` hook at `6EFDA0C–6EFDA30`. The tracked-vehicle interface sub-vtable at `B66A338+0x50` points to `D356F0` (`mov al,1; ret`). `6EF7950` stops after a successful candidate only if that returned flag is zero (`6EF7AFF–6EF7B0C`). Thus Gepard continues through the sorted candidates. Each candidate's cloud-start search can still stop at its first accepted unoccluded start under shipped `PointDiscardMode=2` (`6EF7054–6EF7060`); the retained hit for the same overlap index is replaced only by a smaller `FHitResult.Distance` (`6EF70D0`, comparison at `6EF7115–6EF711E`). “First cloud start” does not mean “first candidate ends the whole Gepard search.”

## LOS and accepted-hit gates

Implementable native skeleton, with runtime-dependent collections left as inputs:

```text
if Points selected and generated cloud is nonempty:
  overlap Visibility sphere; optionally run separate vehicle overlap query
  for each retained overlap record in engine result order:
    build its component/body candidates as above; sort by distance squared
    for each candidate not rejected by (R + 100 cm) search gate:
      for cloud offset in generated order:
        start = originalOrigin + offset
        if start is marked angle-rejected or already origin-occluded: continue
        if index != 1 and start has not already been tested and origin -> start Visibility pretrace blocks:
          mark this start occluded; continue
        trace Visibility from start toward candidate with complex-query params
        if a valid accepted hit is retained and PointDiscardMode == 2: stop starts
      for Gepard, continue to the next candidate and keep nearer accepted hit
```

The cloud iterator `6F03340` reads offsets at context `+0x18`, count at `+0x20`, and adds each to the original origin at `6F033C4–6F03412`. Of its three bitmasks, `+0x00` marks starts whose origin pretrace blocked, `+0x08` marks starts already pretraced, and `+0x10` marks angle-rejected starts. A tested-clear start bypasses **only the repeat pretrace**, then still reaches the candidate callback (`6F03418–6F0348A`); blocked and angle-rejected starts skip the callback. Index 1 bypasses the origin-to-start pretrace at `6F0341D–6F03420`; other eligible offsets call the Visibility pretrace `3CAB860` at `6F0344F`. The callback runs at `6F0348A`, and a true stop return exits at `6F0348C–6F0348E`. The alternative precomputed-start loop uses `6EF8A90` and callback `6F03691` with the analogous stop test. The packed defaults are Points=2, PointDiscardMode=2, AngleDiscardThreshold=10 degrees, PointCloudRadius=50 cm and QueryPointEarlyRejectionDistance=100 cm ([selector table](round8-radial-points-components.md#selector-and-shipped-defaults)); they are initial binary/config values, not observed live state.

`6F030A0` recalculates **only** the `+0x10` angle mask for each overlap component (`6EFDA50–6EFDAC5`), leaving the shared blocked and tested masks at `+0` and `+8` intact across candidates and components of the same gather. For each cloud start index from 2 onward, it compares the normalized vector from original blast origin to that start with the normalized vector from original origin to that component's calculated bounds origin (`+0x598` result), clamps the dot product to `[-1,1]`, and sets the mask bit if `acos(dot) * 180/pi` is **greater** than the angle threshold (`6F031D0–6F032B8`). Indices 0 and 1 are exempt; equality passes. The start positions are built as original origin plus each generated offset at `6F00CA0–6F00CDC`, before this per-component angle call. Normalization uses the native near-zero fallback, so a reference implementation must not divide by zero.

The pretrace query is also conditional. Cloud constructor `6EF63C0` initially leaves its query's `bTraceComplex` byte (cloud `+0x48`) zero. In the shipped nonempty mode-2 branch (`6F00BB2–6F00BCB`), `6F00FD1` copies the main LOS `FCollisionQueryParams` from `v217` into cloud `+0x38` via `35A7EC0`, then replaces its trace tag at `6F00FEA`. That copied query carries `bTraceComplex=1`: the source is set at `6EFFFCF`, copied into the main query at `6F00026`, then into `v217` at `6F00DA5–6F00E6A`. `6F0343E–6F0344F` passes cloud `+0x38` to the origin-to-start Visibility pretrace. Thus this shipped Points branch uses complex-query parameters for both its pretrace and the candidate LOS. Other branch initialization alone does not establish the same flag.

The candidate callback reaches hit builder `6F03720` through `6EF6EE0`. It calls `3CAB670` for a channel-3 (Visibility) single trace at `6F0377D–6F03785`; `6EFFFCF` sets `bTraceComplex=1` for the copied query parameters. An ordinary collision hit must pass original-origin-to-`ImpactPoint` radius check (`6F039E5–6F03A21`), hit-component identity (or a separately enabled same-owner exception, `6F03A27–6F03A5A`) and optional overlap `Item` equality (`6F03A60–6F03A75`). An additional candidate-point/root acceptance branch at `6F0379F–6F039D1` requires its context actor pointer at `+0x58`; an absent pointer bypasses it. Without an accepted trace, a synthetic hit requires context skip-LOS byte `+0x51` (`6F03A8F–6F03A93`). The accepted hit distance is original-origin to accepted `ImpactPoint`, or to the candidate point on the enabled synthetic/root paths (`6F03983–6F039C7`).

For Gepard's inherited tracked-vehicle interface, `B66A338+0x58` points to `1563050` (`xor al,al; ret`), so the same-owner component exception is off. The packed `DefaultGame.ini:300` skip-LOS class list contains `WDDestructionBuilding`, not `WDTrackedVehicle`; helper `6EF8680` supplies the `+0x51` skip byte from that class-list check. The context `+0x58` root/attach-parent exception is populated only through the separate `ActorClassesToIgnoreAttachParentOcclusion` class-list path at caller `6EFFDC0` (corpus loop around lines 841–879); its packed list contains `WDC4`, not Gepard. These static defaults leave Gepard on the ordinary accepted-collision path, conditional on the actual actor/component query results.

## What remains runtime-dependent

`6C2A790` filters the retained component-hit array by component pointer, dropping null or bit-30-flagged targets and repeats; it contains no rule specifically excluding the Gepard's Chassis or TurretSkeleton class. Whether those skeletal components actually appear in Visibility overlaps or block complex LOS depends on registered bodies, shape query flags and runtime collision state. The Points producer can take skeletal body/precomputed-sample branches, while the published GLB omits those two meshes. Neither their participation nor their exclusion follows from the displayed model. The engine's overlap item/body records, resulting component order, level/terrain occluders and actual collision geometry are likewise unavailable from a reference-pose GLB. This report fixes the sampling algorithm and its Gepard class gates, not a deterministic in-game first component or exact health result.
