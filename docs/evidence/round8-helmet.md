# Round 8: Mutable helmet physics assets

Bounded static SDK, corpus, executable and cooked-model check, 2026-10-18. No game process, service, or IDA database was opened. The raw package export stays in the local analysis output directory; this report contains only summarized evidence.

**Current conclusion:** The compiled program has a root-reachable base `__PA:0` tag and conditionally selected helmet `__PA` tags. Mutable deduplicates the selected assets, reuses a sole asset when generated bodies are unmodified, and otherwise builds a combined asset with at most one body setup per bone; the generated Mutable body supplies geometry. The normal inherited `CharacterMesh` has a null physics-asset override and its getter resolves the assigned mesh's asset, so this policy governs the normal generated-mesh path. Runtime parameter values and later mutations remain unknown, so the viewer's exact final asset is unresolved.

## Evidence

Mutable has a dedicated merge list and a separate additional-assets list: `FReferencedPhysicsAssets.PhysicsAssetsToMerge` and `.AdditionalPhysicsAssets` (`sdk/raw/CustomizableObject_structs.hpp:388-396`), embedded in generated component data (`:411-420`). `UCustomizableInstancePrivate` also stores transient clothing and animation-blueprint physics asset collections (`sdk/raw/CustomizableObject_classes.hpp:75-90`). These declarations establish the data model, not which list a given character uses.

The reflected `UCustomizableObjectInstance::SetReplacePhysicsAssets(bool)` is registered at executable RVA `0x66D20A0`. The read-only registration pair at RVA `0xB043BF8` associates that exec with the `SetReplacePhysicsAssets` registration entry; the matching SDK reflected name is `CustomizableObject.CustomizableObjectInstance.SetReplacePhysicsAssets`. Independent Capstone inspection of the exec wrapper shows it reads the bool, gets the instance's `PrivateData` pointer from instance offset `+0x208`, and sets or clears bit `0x10` in the private-data flags dword at `+0x238` (`or ..., 0x10` / `and ..., 0xffffffef`). This identifies the stored switch; it does not by itself establish the consumer's merge-versus-replace effect.

The `UCustomizableInstancePrivate` constructor at RVA `0x6699D70` explicitly writes zero to its flags dword at `+0x238` (`mov dword ptr [rbx+0x238], edi`; `edi` is zero in the constructor sequence). Thus the replace-assets bit starts **off** for a newly constructed private instance. This is a native constructor observation, not a claim about later runtime mutations.

## Mutable source cross-check

The local engine plugin source clarifies what this flag controls. This is a 5.7.4 source snapshot (Build.version changelist 51494982), while the game executable is CL-516586, so use it as a corroborating implementation lead rather than exact-build proof. In `CustomizableObjectInstancePrivate.h:59-65`, `ReplacePhysicsAssets` is bit 4 and its comment says “Merge active PhysicsAssets and replace the base physics asset”; the public instance header exposes the setter at `CustomizableObjectInstance.h:713`, and no `GetReplacePhysicsAssets` API exists in this source tree. The setter in `CustomizableObjectInstance.cpp:6681-6684` sets/clears this flag.

The source separates **collecting/merging** physics assets from **replacing the attached parent’s asset**. During generated-mesh construction, `CustomizableObjectInstance.cpp:5258-5269` parses each Mutable mesh tag `__PA:<index>`, resolves that index through `ModelResources.PhysicsAssets`, and adds a loaded asset to `PhysicsAssetsToMerge`; unresolved soft references are queued and added after load at `:5613-5620`. `GetOrBuildMainPhysicsAsset` at `:1641-1691` deduplicates those assets, returns null for an empty list, reuses the sole asset if the generated physics bodies are unmodified, and otherwise creates a merged asset using the referenced skeletal-mesh physics asset as template when present (falling back to the first active asset). The generated `USkeletalMesh` receives that result at `:2404-2410`.

Separately, `CustomizableObjectSystem.cpp:1390-1398` checks the `ReplacePhysicsAssets` flag before copying the generated skeletal mesh’s physics asset onto an attached parent component. Therefore, the flag does **not** gate collection into `PhysicsAssetsToMerge` or construction of the generated skeletal mesh’s physics asset; it gates replacing the attached parent component’s base physics asset with that generated result. The executable’s default-off flag means that replacement is not enabled initially, absent a later setter call. The cooked export identifies the helmet asset table and head-body constants. The generic JSON's stored constant-mesh `Tags` are empty; the compiled tag operation stream is inspected in the later selection section. No Wardogs callsite has been found to enable the separate attached-parent replacement flag.

The shipped CL-516586 executable independently confirms the core tag-to-merge path. At RVA `0x66C05F0`, Capstone shows a RIP-relative reference to the literal `__PA:` at `0xB043E70`, followed by a prefix test (`0x66C0614-0x66C0634`). On a match, the suffix is parsed to an integer at `0x66C0660`; the code bounds-checks it against the `UModelResources.PhysicsAssets` array (SDK `CustomizableObject_classes.hpp:255-263`, pointer at `+0x78`, count at `+0x80`), then resolves the indexed `TSoftObjectPtr` (stride `0x28`). The resolved `UPhysicsAsset` is appended to `FCustomizableInstanceComponentData.PhysicsAssets.PhysicsAssetsToMerge`: SDK layout gives `ComponentsData` at private-data `+0x108`, component data size `0x150`, `PhysicsAssets` at component `+0xD8`, and `PhysicsAssetsToMerge` at `+0x10`, matching the native array address `+0xE8` and count at `+0xF0`.

The native routine at RVA `0x66BAD60`, called from `0x66C9890` at `0x66CA861`, consumes that same component-data array. Disassembly at `0x66BAE13-0x66BAE60` reads its count/pointer, loops the entries, and calls `0x1433B86D0`; that helper compares each candidate pointer against existing entries and appends only unseen pointers. The branch at `0x66BAE60-0x66BAE75` returns null for an empty set and returns the sole asset directly when the generated physics body's `bBodiesModified` byte (`+0x38`) is clear. Otherwise the routine selects the referenced physics asset when supplied, falling back to the first collected asset (`0x66BAE7A-0x66BAE9D`), creates a new asset through `0x66A96C0`, and copies the template solver settings/type and dedicated-server bit (`0x66BAEC3-0x66BAF18`) before processing the physics bodies. This is the executable's merge/reuse decision; the source tree was only a navigation cross-check. The associated corpus decompilation is unreviewed, so the report relies on Capstone control flow and the SDK field layouts for these conclusions.

Offline extraction of `/Game/Characters/Mutable/MUT_TP_Character` succeeded using the repository extractor and installed cooked content. Its `ModelResources.PhysicsAssets` array contains the simplified player physics asset plus five helmet assets: SuperHeavy 000, Pilot 001, Medium 000, Light 000, and Heavy 001. In `Model.Program.ConstantMeshesPermanent`, indices 76, 81, 83, 88 and 92 each carry one physics body, each with the same BoneId `2523152634`; the object's `BoneNamesMap` maps that ID to `head`. Each of those five records has `bBodiesModified:false` and an empty `AdditionalPhysicsBodies` array. The operation-level selector mapping is resolved below; the body-bearing indices are not a one-to-one list of all five indexed helmet assets, and mesh 92 belongs to the value-6 branch.

Wardogs' `UWDMutableComponent` holds the customizable instance and exposes `AddSharedMutableInstance`, `Init` and layer methods (`sdk/raw/WDGame_classes.hpp:26559-26577`). `UWDMutableCharacterComponent` adds inventory-slot and player-state fields but declares no helmet-specific physics policy (`:35908-35924`). A Capstone scan over all 434,978 corpus function spans found no other direct test/use of `+0x238` bit `0x10`; the only other matching function (`0x40BFD40`) is an unrelated bitfield override routine. The corpus also did not surface a Wardogs setup call to `SetReplacePhysicsAssets`. This rules out a direct bit-test lead in the indexed spans, not an indirect consumer or unindexed generated path. Corpus decompiler text is marked unreviewed and is not treated as semantic proof.

## Finding and boundary

The shipped executable confirms Mutable's policy: it deduplicates the physics assets selected by `__PA:` tags, reuses one selected asset when generated bodies are unmodified, and otherwise builds a combined asset. In that build path it creates at most one result body setup per bone; each setup's geometry comes from the generated Mutable physics body, while matching asset body setups provide template properties. The compiled program links selected helmet values to particular root-reachable tag ops, and root-reachable `__PA:0` metadata on constant mesh 0 has no conditional ancestor in the decoded dependency graph. For the inspected normal `CharacterMesh` constructor chain, `PhysicsAssetOverride` defaults to null and the native getter then obtains the assigned skeletal mesh's physics asset. Thus the compiled normal branch uses Mutable's generated/reused physics-asset policy unless a later override or replacement mutation changes that path. The viewer's concrete parameter values and any later mutation remain unknown; do not claim every referenced helmet asset is active or that one particular helmet's asset is the viewer's final physics asset.

## Per-bone body and shape behavior

The native `0x66BAD60` body loop resolves each `UPhysicsAsset.SkeletalBodySetups` entry by its `BoneName` against the generated Mutable physics body's bone-ID map. When a matching bone has no result yet, it creates one new `USkeletalBodySetup`, copies selected setup properties from that source asset body (bone name, physics type, material, collision response/trace settings, scaling and related flags), then calls a converter with the matched generated Mutable physics-body record and assigns the returned aggregate geometry to the new setup's `AggGeom` (`USkeletalBodySetup` inherits `UBodySetup`; SDK `Engine_classes.hpp:3721` places `AggGeom` at `+0x38`; SDK `Engine_structs.hpp:11352-11364` lays it out as nine separate shape arrays: spheres, boxes, sphyls, convexes, tapered capsules, level sets, skinned level sets, ML level sets and skinned triangle meshes). It then appends that setup once to the result asset's `SkeletalBodySetups` array.

The duplicate-bone branch reuses the already-created result setup index: it updates the shared `bConsiderForBounds` bit and remaps the source asset body's collision-disable-table index. It does not create a second result body and does not call the geometry converter again for that bone. Thus two selected assets whose body setups both target `head` do **not** produce duplicate head bodies or append one asset's `AggGeom` after the other's. The combined asset has at most one head body setup; its shape arrays are populated from the generated Mutable physics-body record. The source setup used when a result body is first created supplies selected body-level template properties. The source-tree cross-check in UE 5.7.4 (`CustomizableObjectInstance.cpp:1356-1430, 1783`) describes the same conversion: it constructs sphere/box/sphyl/tapered-capsule elements from Mutable body data, while convex conversion is commented out in that snapshot. Treat that shape-type detail as corroboration only because the local source CL differs from the game.

This is the builder rule, not proof of the viewer's live output. The compiled branches select tagged helmet constants under explicit helmet/faction/view conditions. The known body-bearing constants (indices 76, 81, 83, 88 and 92) each have one `head` Mutable body with `bBodiesModified:false`. By contrast, the tagged constants for Pilot (`__PA:2`) and Light (`__PA:4`) have no `PhysicsBody` or additional physics bodies on those constants. That only describes those source mesh constants; other selected components and the source physics assets can still affect the generated physics asset. A multi-asset merge or modified Mutable-body path builds the combined asset described above. The default-off replace flag gates the separate parent-component-copy action. For the inspected normal inherited `CharacterMesh`, the constructor initializes `PhysicsAssetOverride` to null and the native getter resolves the assigned mesh's physics asset. Later mutations remain possible, and the viewer's final physics asset still depends on its runtime parameters and mutation path.

The existing `B_WDMoverPlayerCharacter.json` export identifies its `CharacterMesh` as a `WDSkeletalMeshComponentBudgeted` using `/Game/Characters/Player/SK_DefaultCharacter`; the serialized component properties include `SkeletalMesh` but no `PhysicsAssetOverride` field. The generic export may omit null/default properties, so the null default is established by the native constructor chain below, not by this omission. The compiled `__PA` selection and native getter together describe the normal generated-mesh path.

The initial override default is independently resolved by the native constructor chain. SDK `Engine_classes.hpp:2738` places `USkinnedMeshComponent::PhysicsAssetOverride` at `+0x7B0`. Capstone on the shipped executable shows the `USkinnedMeshComponent` constructor at RVA `0x3D5E200` writes zero to `[this+0x7B0]` (`mov qword ptr [rbx+0x7B0], rdi`, after zeroing `edi`). The `USkeletalMeshComponent`, Engine budgeted component, BH budgeted component and Wardogs skeletal component constructors at `0x3D5DA30`, `0x4E75170`, `0x50D0820` and `0x69EC9E0` call the parent constructors but do not write `+0x7B0`; the Blueprint actor constructor chain `0x5282640` → `0x6E67160` → `0x6E7D050` likewise has no `+0x7B0` store. This supports a null constructor default for the normal inherited `CharacterMesh` component. The reflected `SetPhysicsAsset` wrapper at `0x3D9AF30` calls vtable slot `+0xB30` (slot 358); the component override at `0x4422A20` calls the simple store helper at `0x3D83130`, which writes the pointer to `[this+0x7B0]`. The inspected actor constructors do not call this setter path. This resolves the class/constructor default, not all later runtime mutations; an unset override may still cause mesh assignment to use the generated mesh's physics asset.

The native physics-asset getter at RVA `0x3D71170` confirms the default resolution path. It first loads `[this+0x7B0]` and returns that override when non-null (`0x3D71176-0x3D71183`). When null, it selects the current skeletal mesh at `+0x5A8` (with the skinned-asset fallback at `+0x5B0`), then calls or tail-dispatches through vtable slot `+0x3B8` (slot 952) to obtain the mesh's physics asset (`0x3D71185-0x3D71259`). Together with the constructor chain above, this establishes that an unmodified normal component resolves the assigned mesh's own physics asset, including the generated Mutable mesh result. The wrapper/setter can still change the override later; the inspected constructor chain does not establish the absence of every runtime mutation.

## Compiled mesh-tag selection lead

The cooked export does contain the `__PA` strings, but not their mesh-to-op association in the fields previously checked. `Model.Program.ConstantStrings` has six relevant entries, representing `__PA:0` through `__PA:5`; `ModelResources.PhysicsAssets` has six indexed entries. `ConstantUInt32Lists` also has five two-index lists, each beginning with string index 0 and then indices 1-5. In the UE 5.7.4 Mutable runtime source, mesh metadata execution (`CodeRunner.cpp:3062-3130`, opcode `MeshAddMetadataArgs`) can populate `FMesh.Tags` from either a single `ConstantStrings` index or a `ConstantUInt32Lists` list of string indices. This explains why `ConstantMeshesPermanent.Tags` being empty does not rule out tags being added by compiled instructions. The JSON does omit the operation stream; the task-local typed probe decoded the `JsonIgnore` fields and mapped root-reachable tag operations in the next section. Local runtime source is CL-51494982 and serves only as an interpretation aid for the CL-516586 cooked export.

For the five body-bearing constant meshes (indices 76, 81, 83, 88, 92), the exported `PhysicsBody.CustomId` and sole `BodiesCustomIds` entry are both `-1`; each body has BoneId 2523152634 (`head`) and `bBodiesModified:false`. This gives no positive external custom-ID link to a physics asset. The Mutable source uses `AdditionalPhysicsBodies[].CustomId` for AnimBP override-asset lookup (`CustomizableObjectInstance.cpp:2421-2432, 5345-5348`); these five constants have empty `AdditionalPhysicsBodies`, so that alternate route is not evidenced for them. The separate Pilot and Light tag constants inspected below have no generated physics-body record. These facts describe their respective source constants without implying that a viewer selects a particular variant.

## Bytecode-hidden tag operations and root reachability

CUE4Parse's `FProgram` holds the compiled `OpAddress` and `ByteCode` arrays, but both fields are explicitly `[JsonIgnore]` (`E:/WardogsConversion/CUE4Parse/CUE4Parse/UE4/Assets/Exports/CustomizableObject/Mutable/FProgram.cs:21-24`). That is why the generic JSON dump exposed the constant string/list pools and empty `ConstantMeshesPermanent.Tags` while hiding the instructions that add tags. A task-local typed CUE4Parse probe read these fields from the offline `MUT_TP_Character` package. `States[0].Root` and `States[1].Root` are both op address 53644. Before trusting graph results, the probe checked that all 53,645 op offsets are strictly increasing, the root is the last op at byte offset 937,417, and its fixed 30-byte `IN_ADDCOMPONENT` record ends exactly at the 937,447-byte stream end. The op spans also match the local UE 5.7.4 `Operations.h` layouts for all decoded conditional, boolean, parameter and metadata ops (zero mismatches across 32,400 conditionals, 37 `BO_EQUAL_INT_CONST`, 1,111 `BO_AND`, 20 `BO_NOT`, 8 `NU_PARAMETER`, and 1,479 `ME_ADDMETADATA`). Walking control and data dependencies, including conditional predicates and boolean operands, reaches 53,644 nonzero operation addresses. This is a statically decoded dependency graph across alternatives, not a runtime execution trace. The source snapshot is CL-51494982 and the game is CL-516586; structural invariants validate this parse but do not independently prove every opcode layout is identical across those changelists.

The local UE 5.7.4 `Operations.h:1013-1047` defines `ME_ADDMETADATA` with a source mesh plus either a direct `ConstantStrings` tag address or a `ConstantUInt32Lists` address (`IsTagList` bit 0). The executable's program contains direct `__PA:0` through `__PA:5` strings. Root-reachable metadata op 2 tags constant mesh 0 with `__PA:0`; no conditional ancestor for this op was found in the decoded dependency graph. Helmet tag ops include mesh 76 with `__PA:1` (op 561, SuperHeavy), meshes 81 and 83 with `__PA:3` (ops 629 and 642, Medium), and mesh 88 with `__PA:5` (op 699, Heavy). The previous mesh92 claim is corrected: its `ME_CONSTANT` op 727 is root-reachable, but it has no direct `__PA` metadata association and its branch tests helmet value 6 plus third-person view. Root-reachable `__PA:2` ops tag meshes 79, 657 and 1249; root-reachable `__PA:4` ops tag meshes 84, 85, 86, 372, 373, 662, 663, 664, 952, 953, 1254, 1255 and 1256. These variants' per-mesh physics-body records are summarized below.

The selector values and control conditions are present in the compiled operation graph. A branch walk shows: `__PA:1` on mesh 76 is reached on the yes side when helmet parameter 2 equals 1, character-faction parameter 5 equals 1 (Bravo), and view parameter 7 equals 1 (third person); `__PA:3` on mesh 81 is reached at helmet 3, faction 1, view 1, and mesh 83 at helmet 3, faction 2 (Charlie), view 1; `__PA:5` on mesh 88 is reached at helmet 5, faction 1, view 1. `__PA:2` (Pilot, helmet value 2) tags meshes 79, 657 and 1249 under helmet 2 plus character faction 0 (Alpha); this path has no view test. `__PA:4` (Light, value 4) tags the listed constants under helmet 4, third-person view 1, and each faction value 0/1/2. The model parameter descriptors map values 1/2/3/4/5 to SuperHeavy/Pilot/Medium/Light/Heavy item IDs. Their item definitions classify them as `Inventory.Slot.Helmet` (`ID_SuperHeavyHelmet.json:85-90`, `ID_PilotHelmet.json:91-96`, `ID_MediumHelmet.json:85-90`, `ID_LightHelmet.json:82-87`, `ID_HeavyHelmet.json:85-90`). These are compiled branch mappings, not proof of the values used by a particular viewer instance; the serialized default is helmet `-1` and view 0 (first person).

The direct Pilot and Light tagged constants listed above have `PhysicsBody == null` and no `AdditionalPhysicsBodies` in the typed `FMesh` records. In contrast, constants 76, 81, 83, 88 and 92 each have exactly one unmodified Mutable body mapped to `head`; mesh92 is a separate helmet value 6 branch, not Light. Thus the selected Pilot/Light tag constants themselves contribute no generated Mutable body record. This does not by itself establish the full generated physics asset's body count: other simultaneously selected mesh constants and the indexed source `UPhysicsAsset` contents participate in the native builder. Keep the final viewer physics asset unresolved until its parameter values and `CharacterMesh` override/attachment behavior are established.
