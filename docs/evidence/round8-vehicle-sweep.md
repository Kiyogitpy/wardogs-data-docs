## Dispatch and direction

Corpus `callers 0x3A902D0` has only two engine functions: `0x3D2E030` (immediate `UPrimitiveComponent::MoveComponentImpl`, calls at `0x3D2F05D` and `0x3D2F091`) and `0x3D1E9A0` (deferred `UPrimitiveComponent::DispatchBlockingHit`, calls at `0x3D1E9E2` and `0x3D1EA12`). There is no direct Wardogs caller of the actor dispatcher in this call list. In `0x3D2E030`, `0x3CA21B0` supplies the component-sweep hits, a blocking hit is selected, then the two actor notifications fire unless movement dispatch is deferred. Compare local `Engine/Private/Components/PrimitiveComponent.cpp:3140-3146,3335-3355,3380-3397` and `Engine/Private/Components/SceneComponent.cpp:1301-1320`.

The first `0x3A902D0` call notifies the **moving component's owner** with `MyComp=mover`, `OtherComp=Hit.Component`, `bSelfMoved=true`. The second notifies the **struck actor** with `MyComp=Hit.Component`, `OtherComp=mover`, `bSelfMoved=false`. The native `0x3A902D0` reverse branch swaps hit offsets `+0xA4`/`+0xA8` (`MyItem`/`Item`) and both bone names, negates normals, and copies the rest; it does **not** replace `Hit.Component` or `FaceIndex`. The local `Engine/Classes/Engine/HitResult.h:278-291` and `Engine/Private/Actor.cpp:3498-3529` spell out the same rule. The Wardogs vehicle's `0x76740F0` component-hit route forwards its incoming `FHitResult` into a point-damage event (`sub_146BB4D30` receives `a6`), so this direction matters to section matching.

## What the section resolver can use

For a vehicle that **moves into another component**, the hit still names that other component. Vehicle complex-surface lookup first requires the hit component to equal one of its registered static-mesh components; this normally fails before slot lookup. For a **vehicle struck by a moving component**, the reversed hit still names the vehicle's struck component, so registration can pass. Its `MyItem`, however, is now the original sweep hit's `Item`, i.e. the struck body's `InstanceBodyIndex` (or an instanced/collection item index), **not** the triangle material index. The local `Engine/Private/Collision/CollisionConversions.cpp:140-235` sets `Item` from the hit body and leaves `MyItem` alone; `Engine/Classes/Engine/HitResult.h:174-190` initializes `MyItem=-1`. The normal body-instance constructor initializes `InstanceBodyIndex=-1` (`Engine/Private/PhysicsEngine/BodyInstance.cpp:357-359`). Thus an ordinary single-body static-mesh target supplies `MyItem=-1` after reversal; `0x50BF9FD` rejects a negative `MyItem`, and there is no vehicle section. If an instanced target supplies a nonnegative item index, the resolver treats that index as `StaticMaterials[MyItem]` and may select a slot by numerical coincidence. This is an item-index interpretation, not a triangle-derived material match. It remains conditional on that component's actual body/item setup.

The standard move sweep creates `FComponentQueryParams`, and `InitSweepCollisionParams` copies `bTraceComplexOnMove` and `bReturnMaterialOnMove` but does not enable `bReturnFaceIndex` (`Engine/Private/Components/PrimitiveComponent.cpp:2993-3001,3138-3146`). The native query constructor at `0x3C95C30` writes zero across query bytes `+0x12`/`+0x13` (`0x3C95C61`), and the component's sweep-parameter override `0x3D2C220` writes only `+0x10` from component flag `0x29B:5` and `+0x13` from `0x29B:6`; it never writes `+0x12`. Corpus vtable aliases show slot 277 resolves to `0x3D2C220` for `UStaticMeshComponent`, `UInstancedStaticMeshComponent`, `UInstancedWheelMeshComponent`, `UMRotorStaticMeshComponent`, and the listed BH/WD static-mesh subclasses. `0x3D2E030` constructs these params at `0x3D2E553`, invokes slot 277 at `0x3D2E584`, changes only `+0x15` for ignore-touches at `0x3D2E59F`, then calls `0x3CA21B0` at `0x3D2E5E1`. In the scene-query conversion, native `0x3C7C188`/`0x3C7C194` read those query bytes `+0x13`/`+0x12` into the hit-conversion arguments. This proves the ordinary move query's face flag is false for those component types in this executable, independent of its trace-complex setting.

The conversion fields also have executable anchors. The SDK `FHitResult` layout at `sdk/raw/Engine_structs.hpp:9537-9570` puts `FaceIndex` at `+0x00`, `MyItem` at `+0xA4`, and `Item` at `+0xA8`; `+0xE4` lies in unnamed padding, **not** at `FaceIndex`. The sweep conversion (`0x3C7BCE0` → `0x3C6D3A0` → `0x3C6CBA0`) creates each 256-byte hit with `0x3C6E160`; native `0x3C6E1CD` initializes `MyItem` (`+0xA4`) to `-1`. For a valid hit, `0x3C6CBA0` calls `0x3CB3030`: `0x3CB30A7` loads the hit body's index at `+0x0C`, and `0x3CB30AA` stores it into `FHitResult.Item` (`+0xA8`); the other shape/collection branch starts at `0x3CB3140` with `Item=-1` and may replace it with a piece index at `0x3CB31C3`. `0x3CB332A` resets `FaceIndex` (`+0x00`) to `-1`. `0x3C6CBA0` changes the face index and, for a triangle mesh, the `MyItem` material index only under its face-return gate (for example `0x3C6D342`–`0x3C6D37C`); that gate is false for the ordinary movement query. Its initial-overlap branch has the same gated face conversion (`0x3C6CC59`–`0x3C6CC9F`). Local `Engine/Private/Collision/CollisionConversions.cpp:140-235,285-330,414-465` agrees with these roles. Thus an ordinary valid move-sweep hit keeps `FaceIndex=-1` and `MyItem=-1` before actor-direction reversal, while `Item` identifies the struck body or instance.

The section resolver reads `MyItem`, not `FaceIndex` directly, so the decisive difference from the projectile/radial triangle path is the absent triangle-material index and the directional `Item` swap. This closes the **generic native move-sweep conversion** for the traced path. It does not establish a particular live vehicle movement collision or exclude a custom Wardogs query that explicitly enables face indices before a different sweep.
