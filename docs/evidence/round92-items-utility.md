## 1. The action system (IA-1 to IA-7)

### Method

The reflected `TryActivateAction` thunk is `0x5269AD0`; it forwards to `0x5265E40`. That routine checks the component, calls the gate `0x5251400`, and on Allowed or Buffered calls the start routines. Its 80 callers were listed from the corpus xrefs and each was given the action tags it references, by mapping the tag globals it uses to names through the tag registration functions (about 1,900 registered tags mapped). Response types are read through `0x52576E0`, a switch on the type index that returns a pointer to the matching tag list of the definition's response container (types 1, 3, 4, 5, 6 and 10 share the first list; 2, 11, 7, 8 and 9 have their own); the index matches `EBHActionResponseType` in the SDK. The result byte of the gate matches `EBHActionResult` (Allowed 0, Blocked 1, Buffered 3) and the second byte `EBHActionBlockType` (Action 0, State 1, Error 3, Self 4): the stores of `0x0301`, `0x0401`, `0x0101`, `1` and `3` in the gate are Blocked/Error, Blocked/Self, Blocked/State, Blocked/Action and Buffered.

### IA-1 and IA-2. Order, `InterruptOnComplete`, `BlockingStates`

- Gate (`0x5251400`): component and owner valid and local role above simulated proxy, else Blocked/Error. The tag is already in the "starting" list (`+0x710`) gives Blocked/Self. The tag is in the running list (`+0x6E8`) or the second list (`+0x6F8`): Blocked/Self unless definition `+0xB9` is set. The definition's `ActivationContextType` (`+0xB0`) must match the passed struct and the class virtual at slot 93 (`+744`) must accept it. The block map (`+0x1378`) for the tag gives Blocked/Action; the owner's tags are tested against the definition's BlockingStates (slot 5 of the tag-asset interface, `+40`) and RequiredStates (`0x5230980`) for Blocked/State; the buffer map (`+0x1468`) gives Buffered (`0x5256B60`); each `ActionContext` tag of the definition is looked up in the category-block map (`+0x13C8`); last, the class virtual at `+688` (the `CanActivate`) decides.
- Start (`0x5259690`): `sub_145250B20`/`0x525AF90` file the new action's Block, BlockingStates, Buffer and BlockCategories lists into the maps (`0x525AF90` is the instance-level variant; `0x5250B20` the definition-level one, both with the same four maps). Then the lists are read in the order 3, 4, 10, 9, 6 (calls to `0x52576E0` with `3u`, `4u`, `0xAu`, `9u`, `6u`), each running action found in the running array (`+0x598`, stride 20) being cancelled through `0x525A560`; type 4 additionally builds a request (with the cancelled action's saved context) and queues it with `0x525A480`; type 10 calls `0x52521F0`, which walks the pending-request array and removes entries with the listed tag (`0x52520B0`); type 9 compares each running action's context tags (`+0x38` array, `+0x48` parent array of its definition) with the listed categories. After the instance's activation virtual (slot 88, `+704`) the Reactivate actions are requested again with `0x5265E40`. The routine ends with `cmp byte [definition+0xB8]` and, when `bInstantAction` is set, a call to `0x5252EF0` for the new activation.
- End: both `0x525ABE0` (completion, event type 2) and `0x525A560` (cancellation, event type 1) call `0x5258D90` (remove registered responses; also drops buffer records) and broadcast. Only `0x525ABE0` calls `0x52576E0` with type `5u`, loops the list, and cancels each running action with `0x525A560` using this activation as the cause. `0x525ABE0` is reached from `0x5252EF0` (complete by handle) and from Blueprint `Complete`.
- `BlockingStates` while running: `0x525AF90` files the running action under each blocking state in the map at `+0x1418` (5144 decimal); `0x525E450` takes the set of tags just added to the owner, looks each up in that map and cancels every filed activation with `0x5251D20` (cancellation type 0, External). On the owning player's machine (and in standalone play) this runs; `0x525E450` does not run on the authority server. `0x525E6C0` (component setup) takes its address.

### IA-3. `BP_OnCancel`

`0x525A560` finds the running activation (`0x5261B50` lookup), calls the instance's cancel virtual (slot 90, `+720`) with the cancellation context, and keeps the returned response. The branch that uses it requires: response == 1 (Buffer), component flag `+0x559` clear, and the context's first byte (the cancellation type, `EBHActionCancellationType`) == 1 (Interrupted). With `0x525C990` true (the buffering side: byte `+0x55A`, or the predicting-client conditions) it inserts a record for the cancelled tag into the buffer map (hash insert `0x5247760`) whose blocker is the interrupter's tag and id (context `+8` and `+4`); otherwise, if `0x5251A20` (client may queue) holds, the request is filed in the component's own queue at `+0x780`. The consumer is `0x524ECB0` (page section 10.3): when the interrupter ends its blocker record is removed and, with no records left, the gate is called again.

### IA-4. Obfuscated booleans

Definition layout from the SDK: `+0xB8` `bInstantAction`, `+0xB9` `_aaabhcpaaifhekodaalnj`, `+0xBA` `bConsumeAxisInputOnCompletion`, `+0xBB` `_aaacbmicphngedjgincpn`, `+0xBC` `bRebufferAction`. Reads found in the action range `0x5240000..0x5270000`: `+0xB9` in the gate (`0x5251400`, the branch to Blocked/Self at the running-list match) and in `0x5259690` (before the instance is created: look up a running activation of the same tag with `0x5256C80`, cancel it with cancellation type 1); `+0xBB` in `0x5259690` (increments component `+0x708`), `0x525A560` and `0x525ABE0` (decrement, floor 0); `+0xB8` in `0x5259690`; `+0xBC` in `0x524ECB0`. The count `+0x708` has one getter, `0x525C4E0` (`> 0`), and one caller, the mover input producer `0x529BBD0`. In it the result is combined with `length(move input) > 0.0001` and a stored flag (`+0x49`) to set a flag at `+0x48` of the producer, which then rewrites the input record through `0x1452E3850`/`0x141570CD0`; what that does to movement was not followed. No exported asset sets `+0xBB` (page census: 0 of 155), so the path never runs in this build.

## 2. Fire and utility (FU-1 to FU-7)

### FU-1. Throw speed

Listing of `B_Action_ThrowExplosive.CalculateThrowLinearVelocity` (offsets): 0 to 792 build `OutLinearVelocity` from the owner's velocity; `819: if not bUseConsistentVelocity goto 1041`; 842 to 1009 flat path (`ThrowDirection x ThrowVelocity + OutLinearVelocity`); `1041: IsValid(VelocityCurve)`, 1093 to 1297 eye view point, `ClampAngle(pitch, -90, 90)`, `1326: VelocityCurve->GetFloatValue(clamped pitch)`, 1394 to 1552 `ThrowDirection x curve + OutLinearVelocity`. ### FU-4. Collision size

`0x6C8C950(this, transform, hit)` is called from the validation `0x6C8B660` (round 91). It gets the placeable class default object's bounds with `0x3DC0880` (two vectors) and multiplies X by the data `+0x58` (instruction `0x6C8CB44`), Y by `+0x60` (`0x6C8CB53`) and Z (after a factor 0.5) by `+0x68` (`0x6C8CB2D`), then runs `0x143FB6710` (a box sweep) at the hit location; a blocking hit on the visibility channel makes the overlap true and the blocked-reason tag is reported.

### FU-5. After the blast

### FU-7. `EnvironmentKill`

The context tag is not registered natively (no function string for it), so it is consumed in data. ## 4. Building (BD-1 to BD-3)

- BD-1: `0x858D1D0` (`GetTotalBuildCost`): reads `Cost` (`+0x5C`, int), multiplies by the live scale from `0x6CB9970` (1.0 when the pawn has no component), rounds half up, minimum 1, keeps the sign; exactly 0 stays 0. `0x85F1F20` reads the hammer's build amount, multiplies by the data asset factor (`0x85FA770`, `+0x60`), takes the repair multiplier path (below) when finished, then: gain `x / T` with `x = min((1 - progress) * T, min(CeilToInt(A), supplies available) + credit, A)`; credit (`+0x15C`) falls by `x`; when it drops below -0.0001, whole supplies `n = CeilToInt(-credit - min(max(T,1) * 0.0001, 0.1))` are taken (stored through the out pointer) and added back. So supplies are spent per hit. `PlacementCost` is the separate placement charge (BD-3).
- BD-2: `0x85F1F20` calls `0x8578A80` (is fully built) and, when true, `mulss xmm7, [r15+64h]` at `0x85F2020`, where `r15` is the buildable's data asset (`0x85787D0`); `+0x64` is `RepairSpeedMultiplier` in the SDK layout.
- BD-3: `0x85E0050` gets the hammer's `WDItemExtensionData_BuildTool`; `0x85FA170(extension, tag)` reads its `DataRegistryName` (`+0xD0`), asks the data registry subsystem (`0x1446E8130`, `0x1446E9680`) for that registry and fetches the cached row (`0x85DF650`: registry virtual slot 108, then a class check against `WDBuildableDataTableRow`), returning the row's asset (`row +16`). Callers: `0x85F3430`, `0x8605EF0` (build wheel), `0x860E6A0`. `0x85F3430(extension, asset)`: false when the asset's tag (`asset +0x50`) is in the array at extension `+0x1A0` or `+0x1B0`, else true only when `0x85FA170` returns this same asset. `0x85A9CE0` (server placement, reached by a jump from `0x85CC300`, the `WDBuildingInstigator_PlacementComponent` family) calls `0x85F3430` at its start, then `0x85BF0F0` (not decoded; its failure path logs "Failed to place buildable: %s", which is conditional on a debug byte), builds the actor, and calls `0x85F3370(spendingHelper, actor, Action.BuildTool.PlaceSchematic, result)` only when `0x6E6EED0(pawn)` is zero and the test result byte asks for a charge. `0x85F3370` calls `0x85F3070`, which takes the amount. STILL OPEN, reason: the body of `0x85BF0F0` (what it tests besides the three placement-condition classes) was not decoded here.

## 5. The destruction refresh (WK-1)

The Destruction Tailor subsystem's tick is `0x64F1760` (vtable slot 96 of `UBHDestructionTailorSubsystem`). Order: the scorer `0x64F1C40` (round 58), the sort `0x64EC880`, `0x64F2310`, `0x64F25D0`, `0x64EF180`. `0x64F2310` takes the sorted buildings and, for as many as `BuildingUpdatesPerFrame` (settings `+0xB8`, read at `0x64F234D`), compares the scaled camera distance with four ranges (copy of the settings' `TailorRanges[4]` at subsystem `+0x1C0`) and updates a per-building four-bit mask (desired at entry `+157`, current at `+156`, entry stride 160). `0x64F25D0` applies the changed bits: for each changed band it calls `0x3D825B0` (`USceneComponent::SetVisibility(bool, EVisibilityPropagation)` by its shape: it toggles a bit at component `+457`, calls virtual slot 174, and takes a 0, 1 or 2 propagation argument) on the building's pieces for that band, a few per frame; `0x64EF180` places pooled objects (`FBHDestructionTailorObjectPoolData`) at the building's definition positions. The SDK names the four categories Low, Medium, High and External. Nothing in this path writes health, force or the destroyed state. The wiki sentence says "switched on or off"; which pieces (gameplay mesh, cosmetic mesh, pooled actor) belong to each band is not decoded. The identity of `0x3D825B0` is by shape, not by name.

## Doubts

- The tag-name map of call sites is built from the registration functions; a call site using a tag fetched through a non-global path would be missed (the three groups with no tag found are item behaviour helpers whose tag comes from data).
