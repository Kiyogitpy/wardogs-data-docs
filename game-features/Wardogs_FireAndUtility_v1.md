# Wardogs: Fire, Smoke, Throwing and Mine Triggers

*Source: the item definitions under [`data/Wardogs/Plugins/GameFeatures/Items`](https://github.com/Kiyogitpy/wardogs-data-docs/tree/main/data/Wardogs/Plugins/GameFeatures/Items) (Molotov, SmokeGrenade, AT_mine, Claymore, C4, IED), the throw curves and smoke assets under `data/Wardogs/Content`, [`ge-values.json`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/assets/data/ge-values.json) and [`explosive-actors.json`](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/assets/data/explosive-actors.json). Blueprint behaviour comes from the round 8 bytecode listings of the actor Blueprints (kept locally, not in this repository; the [explosive actor evidence](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/docs/evidence/round8-explosive-actors.md) summarises them). Native addresses are RVAs in the restored `CL-516586` executable.*

This page covers what an explosive or throwable does apart from its blast: fire that keeps burning, smoke, how things are thrown, how mines and remote charges are placed and triggered. Blast damage, radius and falloff are not repeated here; they are tabulated per explosive on [Explosives](Wardogs_Explosives_v1.md), with the rules in the [Damage Pipeline](../pipelines/Wardogs_DamagePipeline_v2.md) and the [explosive actor evidence](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/docs/evidence/round8-explosive-actors.md). Prices, unlock levels and buy limits are on the [Item Shop](Wardogs_ItemShop_v1.md) page (section 4).

Labels: **Data** is read straight from the export. **Bytecode** is read from the Blueprint listing of the actor. **Native** is read from the game executable (RVA given). **Derived** is worked out from those values. "Not traced" means nobody has followed it yet.

`GE_MolotovBurning` itself changes no attribute. Its only job is to grant the tag `State.Player.Molotov.Burning`; the damage in the table above comes from the fire field, not from the effect. The Blueprint effect `GE_MolotovBurning` sets only `GrantedTags` (**Data (Blueprint CDO)**, round 17: no duration, stack limit or refresh policy), so those come from the native `UBHGameplayEffect` constructor (`0x5225C65`, **Native**, round 18; a Blueprint class default object copies the native parent's defaults): `Duration` (`+0x30`) 0.0 (store `0x5225C82`), `MaxStacks` (`+0x34`) 1, `StackDurationRefreshPolicy` (`+0x36`) 0 = `RefreshOnSuccessfulApplication`, `StackExpirationPolicy` (`+0x37`) 1 = `RemoveSingleStackAndRefreshDuration` (one dword store `0x1000001` at `0x5225C74`). So a reapplication cannot add a second stack (`MaxStacks` 1) and refreshes the duration policy-wise, but the duration is 0.0. **What a zero duration does at run time** (round 20, evidence level: static-analysis image; virtualized dispatch not removed; the pages read are byte-identical in the analysis and reference images and hold no dispatch stub): the duration pass `0x522D260` loads the effect's class default `Duration` (`+0x30`) and tests it against zero at `0x522D4B3` (`ucomiss`). When equal it jumps to `0x522D700`, which skips the whole timed-expiry block (the end-time comparison at `0x522D4DC` and the removal call `0x522D6F1`, reached through `0x522D6D5`); only a non-zero duration can be removed by this pass. So `Duration` 0.0 means no timed expiry (a standing effect, not an instant one: it stays on the target and keeps its granted tag until something removes it). That is **Derived** from the branch structure; the expiry arithmetic for non-zero durations was not decoded. Other cooked effects use the same default for standing tag effects and name their own removal rule instead (for example `GE_HeavyHelmet_Passive` and `GE_Player_Ghilli_Helmet` set only a removal requirement `ignore State.Player.Vitality.Dead`; `ge-values.json`), which is consistent with that reading.

**What ends the burning tag** (round 20; **Data** plus **Native**): `GE_MolotovBurning` has no removal or ongoing requirement and no application requirement (`ge-values.json`: `removal_requirements`, `ongoing_requirements` null, so native defaults; the only serialized property is `GrantedTags`). `B_Molotov_TriggerVolume` (Blueprint CDO) is a `WDMolotovTriggerVolume` (`WDGameplayTriggerVolume` family; `EffectsToApply` = `GE_MolotovBurning` x1 stack, `bPeriodicQueries` false, allow list `WDMoverCharacter` and `BHBaseVehiclePawn`, `InitialLifeSpan` 45). Its Blueprint `OnEnterTriggerVolume` and `OnExitTriggerVolume` only call the parent function and broadcast `OnTriggerVolumeUpdated`, so the application and removal are native, and `AWDMolotovTriggerVolume` does not override those two virtuals (its vtable at `0xBB222D0` matches `WDGameplayTriggerVolume` `0xB685790` in slots 237 to 240). The inherited enter handler `0x76FBE80` (vtable slot 237, byte offset `+0x768`) applies the tag container (`+0x910`, getter `0x76FBE70`) with `0x5239140`, then applies each entry of `EffectsToApply` (`+0x930`, getter `0x76FBE60`) through `0x5227F20` and stores the returned effect handle in a per-actor record in the array at `+0x948`. The exit handler `0x76FC120` (slot 238, `+0x770`) looks up that record, takes the actor's ability-system component through `0x5318480`, removes the tag container again (`0x5239140` with count -1) and removes every stored effect handle with `0x52355F0` (which calls the same removal routine `0x1452313E0` that the duration pass uses, with stack argument `0x80000001`). So the burning effect is removed when the actor leaves the patch's trigger box (the end-overlap path), not by a timer; since the effect has no timed expiry, leaving the last patch should clear `State.Player.Molotov.Burning` at once, with no lingering burn. That last step is **Inferred**: the end-overlap wiring (`WDTriggerVolume::OnEndOverlap` calling the exit virtual) and the granted-tag release on effect removal were not traced.

Native structure (SDK, `SmokeGrenade` module): `AWDSmokeGrenade` derives from `AWDGrenade` and spawns a grenade actor class (`+0x660`). What the pawn list is used for (vision, AI, targeting) is not traced. **Data (Blueprint CDO)**, round 17: every smoke and signal grenade (`B_SmokeGrenade_*`) sets `BaseFuseTime` 3.0 (the grenade base is 5.0) and lives `PostExplodeLifespan` 10 s after the burst; the spawned world actor `B_WorldSmokeGrenade_White` (all colours inherit it) has `InitialLifeSpan` 175 s; the volume actor `BP_SmokeGrenadeVFX` uses `SphereTraceRadius` 65, `WallHitPosOffset` 100, `Density` 3 and `Height` 1.5 (the trace radius equals the native constructor default `0x869C200`). **Native (static read of the analysis image, round 26):** `AWDSmokeGrenadeVFXActor` fields are `Params` (`FWDSmokeVolumeParams`, `+0x2B8`), `SmokeVolume` (`+0x2E8`), `NiagaraComponent` (`+0x350`), `Pawns` (`+0x358`), one debug bool (`+0x368`), a start-offset float (`+0x36C`, set by `SetStartOffsetSeconds`) and a float at `+0x390` (constructor default -1). `GetEffectiveSmokeTimings` (`0x869F010`) is plain arithmetic on the three asset timings and the start offset: total = max(total - offset, 0.1), fade in = clamp(fade in - offset, 0, total), fade out = max(fade out, 0); so the 120, 64 and 180 s totals above pass through unchanged when the offset is 0. `InitializeSmokeData` (`0x869F280`) builds the `SmokeVolume` point list (`0x869D3FD`) and starts two timers that run `0x869DAF0` after the fade-in delay and `0x869E3D0` later. `UpdatePawnsInBoundingBox` (`0x869E420`) and `UpdatePawnsInSmoke` (`0x869F600`, which uses the point-list overlap test at `0x869D740`) maintain `Pawns`; no native caller was found and the Blueprint `BP_SmokeGrenadeVFX` does not call either function.

Details behind the table:

- **AT mine** (Bytecode): overlap events and the explode decision run on the server only (`HasAuthority`). The mine ignores everything that is not a vehicle. `CheckForVehicle` runs a sphere trace (radius 10) from 20 units above the mine to 100 units up and checks the hit actor against the speed rule; a second path (`CheckForStationaryOverlap`) handles a vehicle already on the mine. Its exact logic is not traced. A mine destroyed by an enemy (`BP_OnDisarmed`) broadcasts `Meta.Progression.Resources.MatchScore.DestroyedDeployable`.
- **Claymore** (Bytecode): the trigger box overlap is checked on the server, then the target must pass `CheckTargetConditions` (player character with a matching gameplay tag, or vehicle above 0 km/h), then the faction check and the line-of-sight trace. From the filtered listing, shooting the Claymore appears to only destroy it (health 1, destroyed-deployable reward), while an explosion nearby sets it off. Which gameplay tag marks a valid player target is not decoded.
- **C4 charge** (Bytecode + Native): the charge sticks to what it hits (`bStickOnImpact` true, attached to the hit component). It has 30 health. When the trigger fires, `OnTriggerExecuted` waits `DelayTillExplosion` seconds when that is above 0, then `DelayedDetonate` calls `Auth_Explode` (`0x6CACE50`, slot 237 `0x6CA80E0`). A 5.0 s repeating check (`CheckOwnerIsAlive`) destroys the charge, without an explosion, when its instigator is no longer valid.
- **IED** (Bytecode): the placed IED (`B_PlaceableIED`) spawns `B_ThrowableIED` at its own position and releases it as a throw with `Action.Throw.Primary.IED`; `B_ThrowableIED` calls the C4 `Detonate`. The IED inherits the C4 detonation code and has no range limit. The trigger item allows one thrown IED at a time (`MaxItemsThatCanBeThrown` 1; UI text "IED already placed" / "No IED placed" / "IED empty").
- **Explosion entry** (Native): explosive actors detonate through `0x6CA8730`; the mine and Claymore have their own Blueprint `CreateExplosion` and do not use it. Both mines initialise the default damage struct in the `AWDLandminePlaceable` constructor (`0x772124F`-`0x77212F0`); see the explosive actor evidence.

## 7. Round 36 additions

Evidence: [round 36 combat evidence](https://github.com/Kiyogitpy/wardogs-data-docs/blob/main/docs/evidence/round36-combat.md), sections 7 and 8.

- **Fire patch size (Data, Blueprint dump).** `B_Molotov_TriggerVolume`'s `BoxComponent` has `BoxExtent` 100 x 100 x 25 (half extents, cm), so each patch trigger box is 200 x 200 x 50 cm and overlaps `Pawn` only. The total spread of the 15 patches is native and not decoded.
- **Impact or fuse (Native).** `B_Molotov` only plays a flight sound. `CollisionExplodeImpactThreshold` (`AWDExplosive +0x498`) is 0.0 in the constructor and no Blueprint sets it; the float is read by the mesh-impact handler `0x6CAB030` (as `a1[294]`), which first tests the bool at `+0x49C`. **Round 39:** `B_Molotov` sets that bool true, so the Molotov explodes on its first impact; the 5.0 s fuse (and depletion of the 50 starting health) are backstops.
- **Armor against fire (Derived from the damage tables).** The fire tick is `Meta.Damage.DamageType.Enviroment`; no row in `DT_GlobalDamage_ArmorData`, `_InfantryData` or `_VehicleData` matches that source, so armor rows do not apply to it. The burst (`Meta.Damage.Explosive.Utility.Molotov`) matches the Explosive armor rows (-85%) and gets -30% against `Armor.SuperHeavy` in `_InfantryData`.
- **Teammates (Derived).** `AlignmentRequired = Friendly` entries exist in `DT_GlobalDamage_InfantryData` for Bullet (-50%) and Large Hammer (-70%) only; none for the Molotov burst or fire tick, and the fire loop has no team check. Whether the mode disables friendly damage elsewhere is not in these tables.
- **What smoke blocks (Native, static).** The only caller of the sight-blocker query (`0x6F4E2D0`) is the aim-assist target manager (`0x6D821E1`). No spotting, lock-on, minimap or damage code calls it, and no smoke effect or tag exists. Whether AI sight traces ignore the smoke is not determined.
