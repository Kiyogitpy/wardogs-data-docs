### How deobfuscated it is

Obfuscated property names are `_` + 21 letters a–p: base 16 of (name length × 2^64 + a 64-bit
hash). The hash depends only on the name, so one token always means the same name; it is not a
standard unsalted hash (CityHash64, FNV, MD5, SHA and CRC32 were tested and did not match), so
names cannot be computed directly. Struct and enum names are not obfuscated.

| | Live usmap | Deobfuscated (v1) | Deobfuscated v2 |
|---|---:|---:|---:|
| Hashed property names | 46,935 | 3,248 | 2,698 (94.3% restored) |
| `Unknown` element types | 5,550 | 451 | 451 |
| Names the SDK corrects (v1 had another field's name) | | | 96 |

How names were restored, in order:

1. Position-by-position pairing with the closed-beta usmap inside segments that line up exactly
   (40,611 names); a token dictionary, since one token means one name everywhere (applied to
   structs the beta lacks or that changed); an order-preserving alignment for structs whose layout
   changed, accepting only exact type matches. Every borrowed name must have the length encoded in
   its token: of 40,613 positional names only 2 failed, and they were dropped. A token resolved to
   two names, or a name claimed by two tokens, is dropped too.
2. **SDK alignment (v2).** `sdk/raw/*_classes.hpp` and `*_structs.hpp` were dumped from this same
   build. They list each class's and struct's own properties by offset, with C++ types, and print
   a real name for many properties the usmap hashes. Each usmap struct is matched to the SDK
   declaration whose `// ScriptStruct Pkg.Name` (or `Class`, `BlueprintGeneratedClass`, ...)
   header has its name. 21,213 structs match; 3 SDK names are declared twice and are skipped.
   Anchors are this build's own readable names and tokens that both sides print. Between two
   anchors, properties are paired in order only when both sides have the same count and every pair
   agrees: compatible type (`TArray<FNone_>` matches any array), the same static-array size, the
   same readable name, the same token, and an SDK name of exactly the length the token encodes. One
   disagreement rejects the whole segment: 13,853 segments paired, 44 rejected (43 type, 1 length).
   Pairs go into the token dictionary.
3. Then the hand-written patches.

The SDK step restored **562** hashed names by alignment. Propagating the dictionary added **0**
more, because every struct that carries one of those tokens is itself in the SDK. No token was
given two names. Two things change v1 names:

- **96 corrections.** At these positions v1 had a closed-beta name that differs from the SDK
  name at the same offset of this build. Fields were reordered between the two builds, and
  positional pairing cannot see a swap between two fields of the same type and name length.
  Examples: `MTrackedVehicleWheelData` `SuspensionPivot` ↔ `DampingCompress` (the value 12,000
  follows `DampingRebound` 17,000); `WDWeaponStats` `Maximum`/`MinimumRandomFiringAnimationOffset`
  (v1 gave Max −0.2 and Min 0.2); `WDBipodAttachmentStanceData` `Min`/`MaxLedgeAngle` and
  `Min`/`MaxTransitionDuration`; `MWheeledVehicleTransmissionData` `ClutchScaleMin`/`Max`;
  `BHAimAssistSettingsData` pull and slow strengths; `GameplayEffect`
  `InheritableGameplayEffectTags` (UE source order). There are 96 corrections in 41 structs.
  `data/` now carries the v2 names; see [`data/` and the v2 usmap](#data-and-the-v2-usmap).
- **12 withdrawn.** The SDK names a different token with the same name, so v1's names on 8
  tokens were withdrawn and those properties are hashed again. Example: `WDWeaponStats+0x15C`,
  which v1 called `bFirstFocalPlane`; the SDK gives that name to `WDSightData[29]`.

FNames ignore case. When the SDK prints a name in a different case (`CONSTANT`, `ability`), the
name is the same, and v1's casing is kept. Names that are new in v2 take the SDK's casing, which is
the casing the name pool stored first (for example `hatindex`).

### `data/` and the v2 usmap

`data/` uses the v2 names since 2026-10-18. The earlier `data/` (2026-10-15) was not read with v1.
It was read with a usmap rebuilt from a memory dump of the live client, whose placeholders have the
form `_<21 letters>_$<HASH>$_$<len>$`, and whose names were carried over from the closed beta by a
separate alignment. With that usmap, the same exporter reproduces the old `data/` byte for byte
(all 6,830 files).

How `data/` was re-exported:

- Same exporter, same output format (`--- export: <class> / <name> ---` and indented JSON per export).
- The usmap is v2 with one change. 236 properties that v2 still types `Unknown` take their element
  type from the memory-dump usmap, at the same index of a struct with the same property count. No
  name was taken from it. v2 alone loses data in 223 files, because CUE4Parse stops reading a struct
  at the first `Unknown` array (for example `WDItemExtensionData_Holdable.MaterialOverrides`). With
  the types filled, it loses none.
- [`_tools/check_data_renames.py`](../_tools/check_data_renames.py) walks the old and new trees of
  every changed file in parallel. Member counts, order and every leaf value must be identical, and
  only member names may differ. Result: 1,971 files changed, 0 value or shape differences, and
  78,637 keys renamed. Each old name maps to one new name everywhere.

## File formats

### `.idmap` — IDA name mapping

The authoritative external artifact is **Dumper-7 binary mapping version 2**, with
magic byte `0xD7`, a packed header, string data, and typed record sections.
It is not an IDA Names-window text export. See the upstream
[layout](https://github.com/Encryqed/Dumper-7/blob/main/Dumper/Generator/Public/Generators/IDAMappingLayouts.h)
and [generator](https://github.com/Encryqed/Dumper-7/blob/main/Dumper/Generator/Private/Generators/IDAMappingGenerator.cpp).

The 2026-10-17 read-only decoder validated its section boundaries and
string references. It contains 3,225 enum records, 21,282 structure/class
records, 3 globals, 9,134 vtables, and **one native exec-function record**:
`AActor::AddComponent`. Do not interpret this file as comprehensive native
function coverage. Its exec-function record stores an RVA; the analysis
image base and build correspondence must be established independently.

The [failed first damage pass](../docs/evidence/damage.md#22-failed-pass-on-the-dump-reconstructed-pe) records the
failure to validate locations against an older reconstructed PE. The later
[restored-input trace](../docs/evidence/damage.md#23-restored-executable-trace) used selected validated
vtable labels from this map. Format validity alone does not establish a
mapping-to-image match.

### `.usmap` — UE class/property metadata

Binary format produced by the community UEDumper fork
([OutTheShade/UnrealMappingsDumper](https://github.com/OutTheShade/UnrealMappingsDumper))
or similar tools. Encodes:

- Class → parent class chain
- Class → property list (name, type, offset, size, flags)
- Enum → value list

Used by:

- **CUE4Parse** — resolves hashed property names when deserializing
  `.uasset` files
- **FModel** — same, for interactive browsing
- **UEDumper** — can import to seed a fresh dump

## How this fits the pipeline

```
.uasset (cooked) ──┐
                   ├─> CUE4Parse ──> data/*.json ──> reference docs
.usmap ────────────┘
                                                              ▲
                                                              │
                                                     cross-ref
                                                              │
.idmap ───────> IDA Pro ──> static RE ─────> formula docs ────┘
```

Short version:

- `.usmap` is a prerequisite for parsing newer UE5 cooked data where
  property names are no longer stored in the asset itself
- `.idmap` supplies type/vtable names for static RE; native registration
  strings and code remain useful where the map has limited coverage

## Usage with IDA Pro

Use the authoritative external path above with a reader/importer compatible
with the binary version, then validate
the selected records against the matching offline image before applying
names or types to an owned analysis database. Do not parse this artifact
as text or add an assumed image base to every field. The restored-input
pass applied selected checked labels to an owned database; a working full
importer is not claimed. Reading the canonical map directly does not
require copying it beside each analysis database.

## Refresh policy

The mappings are build-specific (`CL-516586`). Preserve the `.usmap` needed
to parse the existing exports. Do not generate, substitute or archive
additional IDA maps under the project's single-map policy. If a later
binary no longer matches the authoritative map, record the mismatch;
changing the designated map requires an explicit user instruction.
